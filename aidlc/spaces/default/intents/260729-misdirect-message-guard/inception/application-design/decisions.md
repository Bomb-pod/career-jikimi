## ADR-001: 메시지 전송을 HTTP로, 수신을 WebSocket으로 분리한다

### Status
Accepted (2026-07-29)

### Context

`README.md`의 원래 설계는 전송과 수신을 모두 WebSocket으로 처리했다. 그런데 FR-6.5(판정 대기 중 전송 버튼 비활성화), FR-6.6(부적절 시 확인 팝업), FR-8.1(타임아웃 3~5초, 재시도 1회)를 보면 전송은 **요청하고 답을 기다리는** 성격이다.

WebSocket은 양방향 스트림이지 요청-응답 프로토콜이 아니다. 그 위에 요청-응답을 얹으려면 직접 만들어야 하는 것들이 있다:

- 요청마다 상관 ID를 붙이고, 응답 프레임이 오면 그 ID로 대기 중인 약속을 찾아 해소
- 응답이 안 오는 경우를 위한 타임아웃 타이머
- 재시도 시 중복 전송 방지
- 연결이 끊겼을 때 진행 중이던 요청들의 처리

FR-4.3(낙관적 렌더링 후 ack로 교체)도 이 상관 관리에 얹힌다.

### Decision

**전송 경로를 HTTP로 옮긴다.** `POST /rooms/{id}/messages`가 판정·저장·브로드캐스트를 모두 처리하고, WebSocket은 서버→클라이언트 푸시 전용이 된다. WebSocket으로 클라이언트가 보내는 것은 연결 직후 인증 프레임 하나뿐이다(FR-1.3).

부적절 판정은 409로 반환하며 메시지를 저장하지 않는다. 사용자가 강행하면 `force_log_id`를 붙여 재요청한다.

### Consequences

**좋아지는 것**
- 상관 ID·타임아웃·재시도가 전부 HTTP 클라이언트의 기본 동작이 된다. 직접 만들 코드가 사라진다
- FR-4.3의 ack가 그냥 HTTP 응답이다. 낙관적 렌더링의 교체 시점이 명확하다
- 전송 경로를 `curl`과 일반적인 HTTP 테스트 도구로 테스트할 수 있다. WebSocket 테스트는 도구도 적고 짜기도 번거롭다
- 부적절 판정이 409라는 표준 의미(충돌/전제조건 불만족)에 실려 별도 규약이 필요 없다

**나빠지는 것**
- 부적절 판정 시 왕복이 두 번이 된다. 다만 이때는 사용자가 팝업을 읽고 판단하는 시간이 끼므로 왕복 지연이 체감되지 않는다
- 연결이 두 종류(HTTP + WS)가 된다. 인증도 두 곳에서 한다 — 헤더와 첫 프레임
- 자기가 보낸 메시지가 HTTP 응답과 WebSocket 푸시 양쪽으로 온다. ID 기반 중복 제거가 필요하다 (이미 FR-3.3이 같은 이유로 요구하고 있어 새 부담은 아니다)

**중립**
- 요구사항을 어기지 않는다. FR-4.1·FR-4.2·FR-4.3은 전송 계층을 규정하지 않았다

### Alternatives Considered

**대안 1 — 전부 WebSocket (원래 설계)**
- 장점: 연결이 하나. 지연이 약간 낮다
- 단점: 위 Context의 상관 관리를 전부 직접 구현. 6일 일정에서 이 코드는 순수 비용이며, 버그가 나면 재현이 어렵다
- 기각 이유: 만들어야 할 것이 많고, 그중 어느 것도 이 프로젝트가 증명하려는 가설과 무관하다

**대안 2 — 판정만 REST, 전송은 WebSocket**
- 장점: 판정의 요청-응답 성격은 HTTP로 해결
- 단점: 왕복이 **항상** 두 번. 그리고 전송 경로의 ack 상관 관리는 여전히 남는다
- 기각 이유: 두 방식의 단점만 모았다

### Reversibility

**중간.** 전송 경로를 다시 WS로 옮기려면 클라이언트의 전송 함수와 서버의 엔드포인트를 바꿔야 하지만, `messages.send_message()`의 내부 로직은 그대로 재사용된다. 오케스트레이션을 서비스 함수로 분리해둔 것이 이 되돌림을 싸게 만든다.

## ADR-002: 단일 서비스로 만든다

### Status
Accepted (2026-07-29)

### Context

기능 영역이 다섯 개(auth, friends, rooms, messages, judgment)로 나뉜다. 이를 별도 서비스로 나눌지 하나로 둘지 정해야 한다.

### Decision

**단일 FastAPI 애플리케이션.** 기능별 모듈로 내부를 나누되 프로세스는 하나다. 컨테이너는 `app`과 `db` 둘뿐이다.

### Consequences

- 배포·디버깅·로컬 실행이 단순하다. `docker compose up` 하나로 전부 뜬다(FR-9.1)
- 모듈 간 호출이 함수 호출이라 네트워크 실패 모드가 없다
- 전체를 함께 배포해야 한다. 데모에서는 문제가 아니다
- CON-1(단일 프로세스)과 자연스럽게 맞는다

### Alternatives Considered

**대안 — 판정 서비스 분리**
- 장점: LLM 호출이 무거우므로 독립 확장 가능. 판정 실험을 앱과 무관하게 돌릴 수 있다
- 단점: 서비스 간 호출에 네트워크 실패가 추가된다. 컨테이너·설정·배포가 늘어난다
- 기각 이유: `judgment` 모듈이 이미 다른 모듈에 의존하지 않아(config·db 제외) 격리 목적은 달성되어 있다. 프로세스를 나눠 얻을 게 없다. 팀이 1인이고 기간이 6일이다

**대안 2 — WebSocket 게이트웨이 분리**
- 장점: CON-1(단일 프로세스)의 원인이 `ws_registry`이므로, 그것만 별도 프로세스로 빼면 API 서버는 자유롭게 확장할 수 있다
- 단점: API 서버가 브로드캐스트하려면 게이트웨이에 요청해야 하고, 그 채널(Redis pub/sub 또는 내부 HTTP)이 새로 필요하다. 컨테이너가 셋이 된다. 그리고 확장할 이유가 아직 없다 — 데모 사용자는 시연자 본인과 몇 명뿐이다
- 기각 이유: 해결하려는 문제가 아직 존재하지 않는다. `ws_registry`의 표면을 세 함수로 좁혀둔 것이 이 분리를 나중에 싸게 만든다

### Reversibility

**낮음(쉬움).** `judgment`의 표면이 함수 하나(`judge()`)라 나중에 HTTP 호출로 바꾸는 비용이 작다.

## ADR-003: `seq` 채번이 `rooms`의 데이터 소유권을 넘는다

### Status
Accepted (2026-07-29)

### Context

`components.md`의 소유권 원칙에 따르면 `rooms.last_seq`는 `rooms` 모듈이 소유하고 그 모듈만 써야 한다. 그런데 FR-4.2는 채번과 메시지 저장이 **한 트랜잭션 안에** 있기를 요구한다:

```sql
BEGIN
  SELECT last_seq FROM rooms WHERE id = ? FOR UPDATE
  INSERT INTO messages (..., seq = last_seq + 1)
  UPDATE rooms SET last_seq = last_seq + 1
COMMIT
```

이를 `rooms` 모듈에 두면 `rooms`가 `messages` 테이블에 INSERT하게 되어 소유권이 반대로 깨진다.

### Decision

**`messages` 모듈이 `rooms.last_seq`를 직접 읽고 쓴다.** 소유권 원칙의 명시적 예외로 기록한다.

`rooms`는 여전히 `last_seq`의 스키마와 초기화를 소유한다. 증가만 `messages`가 한다.

### Consequences

- FR-4.2의 원자성이 보장된다. seq 중복도, 구멍도 생기지 않는다
- 소유권 원칙에 예외가 하나 생긴다. 이 문서가 그 예외의 근거다
- `rooms`와 `messages`가 같은 행을 만지므로, 나중에 두 모듈을 다른 서비스로 나누면 이 부분이 걸린다 (ADR-002에서 나누지 않기로 했으므로 지금은 문제없다)

### Alternatives Considered

**대안 1 — `rooms.allocate_seq()` 함수를 제공하고 `messages`가 호출**
- 장점: 소유권 원칙 유지
- 단점: 그 함수가 트랜잭션을 열면 `messages`의 트랜잭션과 중첩되고, 열지 않으면 잠금이 저장까지 이어지지 않아 원자성이 깨진다. 트랜잭션 객체를 인자로 넘기면 결국 같은 트랜잭션을 공유하는 것이라 캡슐화가 이름뿐이다
- 기각 이유: 형식적 소유권을 지키고 실질을 잃는다

**대안 2 — DB 시퀀스나 `AUTO_INCREMENT` 사용**
- 장점: 채번이 DB에 맡겨져 잠금이 필요 없다
- 단점: MariaDB의 `AUTO_INCREMENT`는 테이블 전역이라 **방 안에서 단조 증가**를 만들 수 없다. FR-4.2가 요구하는 것은 `(room_id, seq)`의 방별 연속성이다
- 기각 이유: 요구사항을 충족하지 못한다

### Reversibility

**낮음(쉬움).** 채번 방식을 바꾸는 것은 함수 하나의 내부 변경이다. 다만 이미 저장된 메시지의 seq는 그대로 두어야 한다.

## ADR-004: 프론트엔드 상태를 Zustand로 관리한다

### Status
Accepted (2026-07-29)

### Context

관리할 상태는 인증 토큰, 친구 목록, 방 목록과 안 읽은 개수, 현재 방의 메시지, degraded 플래그, 토스트 큐다.

특징이 하나 있다 — **상태 변경의 상당수가 React 컴포넌트 밖에서 일어난다.** WebSocket 수신 핸들러가 메시지를 받아 목록에 넣고, 안 읽은 개수를 올리고, 토스트를 띄운다.

### Decision

**Zustand.** 스토어 하나에 슬라이스를 두고, WebSocket 핸들러는 `useChatStore.getState()`로 접근한다.

`degraded`는 스토어의 메모리에만 둔다 — `localStorage`·`sessionStorage`에 쓰지 않는다(FR-8.3이 새로고침 시 초기화를 요구한다).

### Consequences

- WS 핸들러에서 상태를 바꾸는 코드가 한 줄이다
- 선택자 기반 구독이라 메시지 하나 도착에 전체가 리렌더되지 않는다
- 의존성이 하나 늘어난다 (작다)
- 팀이 Zustand를 모르면 배우는 시간이 든다 — 표면이 작아 실질적 비용은 낮다

### Alternatives Considered

**대안 1 — React Context + useReducer**
- 장점: 의존성 없음. 러닝커브 없음
- 단점: Context는 컴포넌트 트리 안에서만 접근 가능하다. WS 핸들러에서 dispatch하려면 ref로 새어나가게 하거나 이벤트 버스를 두어야 한다. 그리고 Context 값이 바뀌면 소비자 전체가 리렌더된다
- 기각 이유: 이 앱의 상태 변경 절반이 컴포넌트 밖에서 온다. Context가 가장 약한 지점이 정확히 여기다

**대안 2 — Redux Toolkit**
- 장점: 구조가 명확하고 devtools가 좋다
- 단점: 설정과 보일러플레이트가 6일 일정에 과하다
- 기각 이유: 이 규모에 얻는 것보다 드는 게 크다

**대안 3 — TanStack Query**
- 장점: 서버 상태 캐싱·재검증이 공짜
- 단점: WebSocket 푸시로 들어오는 실시간 갱신과 쿼리 캐시 무효화를 맞추는 게 오히려 복잡하다
- 기각 이유: 이 앱의 서버 상태는 캐싱이 필요할 만큼 무겁지 않고, 실시간 갱신이 주된 경로다

### Reversibility

**낮음(쉬움).** 스토어 접근이 훅 하나로 모여 있어 교체 시 그 지점만 바꾼다.

## ADR-005: LLM 출력을 Structured Outputs로 강제한다

### Status
Accepted (2026-07-29)

### Context

FR-6.3은 모델이 0.0~1.0의 점수만 반환하고 서버가 임계값으로 가르기를 요구한다. 프롬프트로 "숫자만 답하라"고 요청할 수 있으나 모델이 설명을 덧붙이면 파싱이 깨진다.

이건 판정 **품질**이 아니라 **안정성** 문제다. 파싱 실패는 FR-8의 실패 처리(타임아웃·재시도·degraded)를 발동시키는데, 그 경로는 네트워크·API 장애를 위한 것이지 형식 오류를 위한 것이 아니다.

### Decision

**OpenAI Structured Outputs를 `strict: true`로 사용한다.**

```python
response_format={
  "type": "json_schema",
  "json_schema": {
    "name": "verdict",
    "strict": True,
    "schema": {
      "type": "object",
      "properties": {"score": {"type": "number"}},
      "required": ["score"],
      "additionalProperties": False
    }
  }
}
```

### Consequences

- 파싱 실패라는 실패 유형이 사라진다
- 프롬프트가 형식 지시에서 해방되어 판정 기준 서술에 집중할 수 있다
- Structured Outputs를 지원하는 모델을 써야 한다. **Code Generation에서 모델 ID와 지원 여부를 확인한다**
- `score` 하나만 받는 스키마이므로, 나중에 근거 문장을 받고 싶으면 스키마를 늘려야 한다 (쉽다)

### Alternatives Considered

**대안 1 — JSON 모드 + 수동 파싱**
- 장점: 지원 모델 범위가 넓다
- 단점: JSON임은 보장되나 필드 구조는 프롬프트에 의존한다. 파싱 실패 처리가 여전히 필요
- 기각 이유: 절반만 해결한다

**대안 2 — Tool calling**
- 장점: 스키마 보장. 여러 도구가 필요할 때 확장성이 좋다
- 단점: 응답 구조가 한 겹 깊어지고, 모델이 도구를 안 부르는 경우를 처리해야 한다
- 기각 이유: 도구가 하나뿐이라 얻는 게 없다

**대안 3 — 평문 숫자만 요청**
- 장점: 가장 단순
- 단점: 형식이 보장되지 않는다
- 기각 이유: 정확히 이 문제를 피하려고 이 ADR을 쓰고 있다

### Reversibility

**낮음(쉬움).** `judgment` 모듈의 호출부 한 곳만 바꾼다.

## ADR-006: Alembic으로 스키마를 관리한다

### Status
Accepted (2026-07-29)

### Context

6일 일정에서 스키마는 여러 번 바뀐다. 이번 워크플로에서만 이미 두 컬럼이 늘었다 — `room_members.last_read_seq`(FR-5.2), `messages.misdirect_reported_at`(FR-11.3).

### Decision

**Alembic.** 초기 스키마부터 마이그레이션으로 만든다. `create_all()`을 쓰지 않는다.

async 드라이버(`asyncmy`)를 쓰므로 `migrations/env.py`를 async용으로 구성한다.

### Consequences

- 스키마를 바꿔도 데이터가 남는다
- 변경 이력이 파일로 남아 "왜 이 컬럼이 생겼나"를 추적할 수 있다
- 초기 설정에 시간이 든다 (async 설정 포함 약 30분)
- 컨테이너 기동 시 `alembic upgrade head`가 먼저 돌아야 한다 (FR-9.2의 순서에 편입)

### Alternatives Considered

**대안 — `create_all()`로 시작하고 나중에 Alembic 도입**
- 장점: 초반 30분을 아낀다
- 단점: 스키마를 바꿀 때마다 DB를 지우고 → 계정 다시 만들고 → 방 다시 만들고 → 판정이 돌 만큼(N=10) 메시지를 다시 쌓아야 한다. 한 번에 10분 이상이며, 데모 리허설 중에 이게 터지면 뼈아프다
- 기각 이유: 세 번째 스키마 변경에서 본전이고, 세 번은 확실히 넘는다

**대안 2 — 손으로 쓴 SQL 마이그레이션 파일 + 적용 스크립트**
- 장점: Alembic 의존성과 async 설정이 필요 없다. 무슨 SQL이 도는지 눈에 그대로 보인다
- 단점: 어디까지 적용했는지 추적하는 버전 테이블을 직접 만들어야 한다. 그게 Alembic이 하는 일의 절반이다. 자동 생성이 없어 모델과 스키마가 어긋나도 알려주지 않는다
- 기각 이유: Alembic이 해주는 것을 조금 더 나쁘게 다시 만드는 셈이다. 절약되는 것은 의존성 하나뿐이다

### Reversibility

**높음(어려움).** 이 결정만 되돌리기 어려운 이유는, 나중에 Alembic을 도입하려면 이미 존재하는 스키마를 기준으로 초기 마이그레이션을 손으로 맞춰야 하기 때문이다. 반대 방향(Alembic → create_all)은 쉽지만 그럴 이유가 없다.

**그래서 지금 정하는 것이 맞다.**

## ADR-007: degraded 상태를 클라이언트가 소유한다

### Status
Accepted (2026-07-29)

### Context

FR-8.3은 degraded를 "모든 방에 적용, 브라우저 탭의 메모리에만 저장, 새로고침 시 초기화"로 규정한다. 그러면 서버는 클라이언트가 degraded인지 알 수 없다.

그런데 `verification_status`를 정하는 것은 서버다(FR-7.1). 서버가 모르는 상태에 따라 서버가 값을 정해야 하는 모순이 생긴다.

### Decision

**클라이언트가 `degraded` 플래그와 프로브 차례를 판단해 요청에 실어 보낸다.** 서버는 그 값을 믿고 판정을 건너뛴다.

```
POST /rooms/{id}/messages  { text, degraded: true }
```

프로브 차례(5번째 메시지, FR-8.5)도 클라이언트가 세어 `degraded: false`로 보내면 서버가 판정을 시도한다.

### Consequences

- FR-8.3의 "탭 단위, 새로고침 시 초기화"가 자연스럽게 성립한다. 서버에 상태가 없으니 지울 것도 없다
- 서버가 무상태로 유지된다
- **클라이언트가 서버의 검증을 우회할 수 있다.** `degraded: true`를 항상 보내면 판정이 절대 돌지 않는다
- 탭을 두 개 열면 각 탭의 degraded가 독립적이다 (ASM-2가 이미 기록한 한계)

### Alternatives Considered

**대안 1 — 서버가 사용자별 degraded 상태를 보관**
- 장점: 우회 불가. 탭 간 일관성
- 단점: FR-8.3의 "새로고침 시 초기화"를 만족시키려면 서버가 세션 개념을 가져야 하는데, 이 앱의 JWT는 무상태다. 세션 저장소가 새로 필요하다
- 기각 이유: 요구사항이 명시적으로 탭 단위·새로고침 초기화를 정했고, 그 요구사항 자체가 "장애가 이미 끝났을 수 있으니 다시 시도한다"는 합리적 근거를 갖는다

**대안 2 — 서버가 자체적으로 API 장애를 감지해 degraded 판단**
- 장점: 클라이언트를 믿지 않아도 된다
- 단점: 사용자 동의(FR-8.2)가 degraded 전환의 전제인데, 서버가 스스로 판단하면 그 동의를 건너뛴다
- 기각 이유: 요구사항의 동의 절차와 충돌한다

### Reversibility

**중간.** 서버 소유로 옮기려면 세션 저장소가 필요하고 FR-8.3을 고쳐야 한다. 요구사항 변경을 수반한다.

### 보안 메모

우회 가능성은 **이 데모의 위협 모델에 없다.** 사용자가 자기 자신의 오발송 경고를 우회하는 것은 자해이지 공격이 아니다. 다중 사용자 환경에서 관리자가 검증을 강제해야 하는 제품이라면 이 결정은 성립하지 않는다.

## ADR-008: 지표 산출을 CLI로 노출한다

### Status
Accepted (2026-07-29)

### Context

FR-7.5는 산출 가능한 지표 일곱 가지와 산출 불가능한 recall을 규정한다. `judgment.compute_metrics()`가 그것을 계산하는데, **결과를 어떻게 꺼내 볼지**가 정해지지 않았다.

### Decision

**CLI 명령으로 노출한다.** `docker compose exec app python -m app.judgment.report`가 지표를 표로 출력한다.

UI 화면을 만들지 않는다.

### Consequences

- 화면·라우팅·권한 처리가 필요 없다. 6일 일정에서 값어치가 낮은 곳에 시간을 쓰지 않는다
- 발표 때 터미널에서 바로 보여줄 수 있다 — 오히려 실험 도구답게 보인다
- 관리자 화면이 필요해지면 나중에 같은 함수를 라우터에 붙이면 된다

### Alternatives Considered

**대안 1 — 관리자 화면**
- 장점: 보기 좋다
- 단점: 인증·권한·화면·차트가 붙는다. 이 프로젝트의 가설과 무관한 작업이다
- 기각 이유: 비용 대비 얻는 것이 없다

**대안 2 — `GET /metrics` 엔드포인트 (JSON)**
- 장점: 프로그램으로 소비 가능. 나중에 화면을 붙이기 쉽다
- 단점: 누가 볼 수 있는지 정해야 한다. 판정 로그는 대화 내용의 파생물이라 아무나 보면 안 된다
- 기각 이유: 권한 설계가 붙는 순간 CLI보다 비싸진다. 컨테이너에 들어갈 수 있는 사람은 이미 DB도 볼 수 있으므로 CLI에는 그 문제가 없다

### Reversibility

**낮음(쉬움).** `compute_metrics()`는 그대로 두고 표현 계층만 추가하면 된다.
