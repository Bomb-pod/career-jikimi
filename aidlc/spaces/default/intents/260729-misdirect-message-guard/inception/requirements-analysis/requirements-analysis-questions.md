## Q8. (후속 — 신규) 채팅방을 열어놓지 않은 상태에서 새 메시지가 오면 어떻게 알리는가?

> 사용자 질문: "내가 채팅방을 열어놓지 않더라도 새로운 채팅이 들어왔을 때 알람이 와있긴 한 거지?"
>
> **배선은 이미 있다.** WebSocket 연결이 사용자당 1개이고 payload의 `room_id`로 여러 방을 멀티플렉싱하므로, 다른 방을 보고 있어도 그 방 메시지가 같은 연결로 들어온다. 서버는 방 참여자 전원에게 브로드캐스트한다. 정의되지 않은 것은 **클라이언트가 그걸 받아서 무엇을 하는가**다.
>
> **한계를 먼저 못박는다.** 브라우저를 완전히 닫으면 WebSocket도 끊기고, 그 상태의 알림은 Service Worker + Web Push(푸시 서버·VAPID 키·구독 관리)를 요구한다. 이번 범위 밖이다. 아래 선택지는 모두 **앱이 탭에 떠 있는 동안**을 전제한다.
>
> `README.md`의 "만들지 않는 것"에 있는 **읽음 표시**(상대가 내 메시지를 읽었는지)와는 다른 기능이다. 여기서 묻는 것은 내가 안 읽은 것이 몇 개인가다.

- A. 방 목록에 **안 읽은 개수 배지**만 — 마지막으로 읽은 `seq`를 방별로 기억하고 그보다 큰 메시지 수를 센다. 비용이 작고 채팅앱의 기본 기대치다
- B. 배지 + **앱 내 토스트** — 다른 방 메시지가 오면 화면 모서리에 잠깐 뜨고, 누르면 그 방으로 이동한다
- C. 배지 + **브라우저 알림**(Notification API) — 탭이 백그라운드여도 OS 알림이 뜬다. 권한 요청 흐름이 붙지만 Service Worker는 필요 없다
- D. 아무것도 하지 않는다 — 방에 들어가야만 새 메시지가 보인다
- E. Not yet defined
- X. Other (please specify)

[Answer]: B. 배지 + 앱 내 토스트

## Q9. (후속 — 측정 가능성) API가 판정하는데 성능 지표는 어디서 도출하는가?

> 사용자 질문: "api로 적절여부를 판별하는 거면 성능 검사와 지표는 어떻게 도출해?"
>
> 구조적 비대칭이 드러났다. 사용자 피드백은 **모델이 부적절이라 판정한 건에서만** 나온다 — 팝업이 뜨고 사용자가 취소/강행을 선택하기 때문이다. 적절로 판정된 메시지는 그냥 전송되고 아무 신호도 남기지 않는다. 검증이 꺼졌거나 문맥이 부족했던 메시지도 마찬가지다.
>
> 결과적으로 **precision은 근사치를 낼 수 있지만 recall은 실사용 로그만으로 산출할 수 없다.** 놓친 오발송(FN)의 모수를 알 방법이 없기 때문이다. `intent-statement.md`가 recall을 "측정하되 우선순위 아님"으로 적은 것은 이 사실을 모른 채 쓴 것이다.
>
> precision을 1순위로 둔 판단 자체는 이 사실로 오히려 뒷받침된다 — 라이브에서 측정 가능한 것이 그것뿐이다.

- A. 오발송 신고 버튼을 추가한다 — 전송된 메시지에 "잘못 보냈어요"를 달아 FN 신호를 수집한다. 적절 판정·검증 꺼짐·문맥 부족 구간의 사각지대를 메운다
- B. 추가하지 않고 명시만 한다 — precision·flag rate·지연·비용만 산출하고, recall은 "라벨 데이터셋이 필요해 트랙 2로 분리"라고 요구사항에 적는다
- C. 신고 버튼을 Should로 — 범위에 넣되 일정이 밀리면 자른다
- D. 다른 방법을 찾는다
- X. Other (please specify)

[Answer]: A. 오발송 신고 버튼을 추가한다

## Consolidated Summary Confirmation — 보충 기록

위 `## Consolidated Summary Confirmation`의 `Looks correct` 답변은 **Q9가 추가되기 전** 시점의 것이다. Q9는 요구사항 산출물을 쓰던 중 사용자가 측정 가능성을 물어 생겼고, 그 답변(신고 버튼 추가)이 곧바로 FR-11로 편입되었다.

즉 Q9의 내용은 요약 확인 게이트를 거치지 않았다. 다만 Q9 자체가 구조화 질문으로 사용자에게 직접 제시되고 답변된 항목이므로, 그 답변이 해당 범위에 대한 사람의 확인 역할을 한다. 이 단계 전체는 뒤따르는 승인 게이트가 다시 덮는다.

다음에 이 스테이지를 돌 때는, 산출물 작성 중 신규 문항이 생기면 요약 확인을 다시 돌리는 편이 프로토콜에 더 맞다.
