# Business Rules — messaging

`../../../inception/requirements-analysis/requirements.md`의 FR-3.3(히스토리)·FR-4.1~FR-4.4·FR-6.4~FR-6.6·FR-7.1(판정 안 함 상태)·FR-8.2~FR-8.6·FR-11을 판정 가능한 규칙으로 편 것이다. 단위 경계는 `../../../inception/units-generation/unit-of-work.md`, 배정은 `../../../inception/units-generation/unit-of-work-story-map.md`, 컴포넌트 소유권은 `../../../inception/application-design/components.md`, 메서드 서명은 `../../../inception/application-design/component-methods.md`, 트랜잭션 형태는 `../../../inception/application-design/services.md`를 따른다.

## 전송 순서

### BR-4.1 · 저장 먼저, 브로드캐스트 나중

| 항목 | 내용 |
|---|---|
| 규칙 | DB 커밋이 **완료된 뒤에** 브로드캐스트한다 |
| 위반 시 | DB 쓰기 실패인데 화면엔 보이고, 새로고침하면 사라진다 |
| 근거 | FR-4.1, NFR-3 |

**브로드캐스트는 트랜잭션 밖이다.** 안에 두면 커밋 전에 나가고, 롤백되면 유령 메시지가 남는다.

### BR-4.2 · 채번은 저장과 한 트랜잭션

| 항목 | 내용 |
|---|---|
| 규칙 | `SELECT rooms.last_seq FOR UPDATE` → `+1` → `INSERT messages` → `UPDATE rooms.last_seq`를 **하나의 트랜잭션**으로 |
| 잠금 범위 | 그 방의 `rooms` 행 하나. 다른 방은 영향 없음 |
| 근거 | FR-4.2, ADR-003 |

**트랜잭션을 나누면 seq가 중복되거나 구멍이 생긴다.** `UNIQUE (room_id, seq)`가 최종 방어선이지만 거기까지 가면 이미 요청이 실패한 것이다.

### BR-4.3 · LLM 호출은 트랜잭션 밖

| 항목 | 내용 |
|---|---|
| 규칙 | 판정은 트랜잭션을 열기 **전에** 끝낸다 |
| 이유 | 3~5초짜리 외부 호출을 잠금 안에 넣으면 그동안 그 방의 모든 전송이 막힌다 |
| 근거 | ADR-001, NFR-1 |

## 판정 분기

### BR-6.1 · `verification_status` 결정 순서

호출자 상태를 위에서부터 판정하고 **첫 번째로 걸리는 것을 적용**한다.

```
1. 발신자 토글이 꺼짐            --> disabled           (호출 안 함)
2. degraded 이고 프로브 차례 아님 --> degraded           (호출 안 함)
3. 방 메시지 수 < AI_CONTEXT_N   --> skipped_no_context (호출 안 함)
4. 그 외                         --> judgment.judge() 호출
      +-- appropriate  --> ok
      +-- inappropriate --> 저장 안 함, 409 반환
      +-- failed        --> failed
```

<!-- Text fallback: verification_status는 발신자 토글이 꺼졌으면 disabled, degraded 상태이고 프로브 차례가 아니면 degraded, 방 메시지가 N개 미만이면 skipped_no_context, 그 외에는 모델을 호출해 결과에 따라 ok, 409, failed로 나뉜다. -->

**순서가 중요하다.** 토글이 꺼져 있으면 콜드스타트 여부를 따질 필요가 없고, degraded면 문맥 개수를 셀 필요가 없다. 싼 판정부터 한다.

**2번이 3번보다 앞인 것**에 실질적 의미가 있다 — degraded 상태에서는 문맥이 충분해도 호출하지 않으므로, 문맥 개수 조회(DB 접근 1회)를 아낀다.

### BR-6.2 · 콜드스타트

| 항목 | 내용 |
|---|---|
| 조건 | 그 방의 메시지 수 < `AI_CONTEXT_N` (기본 10) |
| 결과 | 판정 없이 전송. `skipped_no_context`. **판정 로그도 남기지 않는다** |
| 근거 | FR-6.4 |

문맥이 없으면 판단이 불가능하다. 억지로 판정하면 노이즈만 쌓인다.

### BR-6.3 · 부적절 판정은 저장하지 않는다

| 항목 | 내용 |
|---|---|
| 결과 | **409** + `{ log_id, score }`. `messages` INSERT 없음 |
| 클라이언트 | 확인 팝업 표시. 입력창 텍스트 유지 |
| 근거 | FR-6.6, ADR-001 |

**409는 오류가 아니라 정상 분기다.** 클라이언트가 예외로 처리하면 안 된다.

### BR-6.4 · 강행 전송

| 항목 | 내용 |
|---|---|
| 트리거 | **두 팝업 모두** — 부적절 판정의 "보내기", 판정 실패의 "수락" |
| 검증 | U2의 `get_log_for_force()` (BR-6.9 in judgment-core) |
| 결과 상태 | 로그의 `verdict`에서 파생 — `inappropriate` → `flagged_sent`, NULL(실패) → `failed` |
| `user_action` | 둘 다 `'sent'` — "경고/미검증을 알고도 보냈다" |
| 근거 | FR-6.6, FR-8.3 |

**부적절 판정과 판정 실패가 같은 재요청 경로를 쓴다.** 둘 다 "이미 판정을 시도했고 사용자가 결정했다"이므로 `force_log_id`의 의미에 정확히 맞는다.

**검증 없이 `force_log_id`를 믿으면 판정 우회 경로가 된다.** 소유자·방·미소진·부적절판정·**텍스트 일치**를 모두 확인한다.

### BR-6.5 · 취소

| 항목 | 내용 |
|---|---|
| 트리거 | 팝업에서 "취소" |
| 결과 | 메시지 저장 안 함. 판정 로그의 `user_action='cancelled'`만 기록 |
| 입력창 | 텍스트 유지 |
| 근거 | FR-6.6, FR-7.2 |

## 실패 처리

### BR-8.1 · 실패 시 조용히 보내지 않는다

| 항목 | 내용 |
|---|---|
| 규칙 | 판정 실패를 사용자에게 알리지 않고 전송하는 경로는 없다 |
| 근거 | FR-8.2 — 사용자는 검증받았다고 믿고 있다 |

### BR-8.2 · 세션 첫 실패

| 항목 | 내용 |
|---|---|
| 트리거 | degraded가 아닌 상태에서 판정 실패 |
| 결과 | "검증 서버에 연결할 수 없습니다. 그래도 보내시겠습니까?" 팝업 |
| 전송 | 사용자 응답 **전에는 전송하지 않는다** |
| 근거 | FR-8.2 |

### BR-8.3 · 수락 시

| 항목 | 내용 |
|---|---|
| 그 메시지 | `failed`로 전송 — **호출을 실제로 시도했기 때문** |
| 방법 | 받은 `log_id`를 `force_log_id`로 실어 재요청한다 (BR-6.4). `degraded` 플래그만 세워 재요청하면 BR-6.1 우선순위에 걸려 `degraded`로 저장되어 시도한 사실이 사라진다 |
| 이후 상태 | **재요청이 끝난 뒤** degraded로 전환. 순서가 바뀌면 그 메시지가 `degraded`가 된다 |
| degraded 범위 | **모든 방.** 방을 옮겨도 다시 묻지 않는다 |
| 저장 위치 | 브라우저 탭 메모리. 새로고침·새 탭이면 초기화 |
| 근거 | FR-8.3 |

**그 메시지가 `degraded`가 아니라 `failed`인 것**이 6값이 모두 도달 가능해지는 지점이다. 시도했으므로 `failed`, 이후 시도하지 않는 것들이 `degraded`.

### BR-8.4 · 거절 시

| 항목 | 내용 |
|---|---|
| 결과 | 전송 취소. 입력창 텍스트 유지 |
| UI | 입력창 옆에 **"다시 시도" 버튼** 표시 |
| 버튼 동작 | 같은 텍스트로 검증부터 다시 시작 |
| 상태 | degraded로 넘어가지 **않는다** |
| 근거 | FR-8.4 |

**"다시 시도"가 어느 메서드에 대응하는지가 `application-design`에서 이월된 항목이었다.** 별도 메서드가 아니라 `send_message()`를 같은 인자로 다시 부르는 것이다. 서버 측에 새 표면이 필요 없다.

### BR-8.5 · 프로브

| 항목 | 내용 |
|---|---|
| 조건 | degraded 상태에서 **5번째 메시지마다** |
| 카운터 범위 | **사용자 전역** — 방을 옮겨도 이어서 센다 |
| 성공 | degraded 해제 + "AI 검증이 다시 켜졌습니다" 알림. 상태는 판정 결과대로 |
| 실패 | 팝업 없이 degraded 유지. 그 메시지는 **`failed`** |
| 근거 | FR-8.5 |

**카운터 범위가 사용자 전역인 것이 `application-design`에서 이월된 항목의 해소다.** degraded 자체가 모든 방에 적용되므로(BR-8.3) 카운터도 같은 범위여야 한다. 방 단위로 세면 방을 옮길 때마다 카운터가 리셋되어 프로브가 거의 안 돈다.

카운터는 degraded 진입 시 0으로 시작하고, degraded가 해제되면 사라진다.

### BR-8.6 · 미검증 배지

| 항목 | 내용 |
|---|---|
| 대상 | `failed`, `degraded`, `skipped_no_context` |
| 제외 | `ok`, `flagged_sent`, `disabled` |
| 근거 | FR-8.6 |

**`disabled`에 배지를 달지 않는 이유** — 사용자가 스스로 끈 것이라 이미 알고 있다. 배지는 "검증받았다고 믿었는데 아니었다"를 알리는 장치다.

`flagged_sent`도 제외한다 — 검증을 받았고 경고까지 봤다.

## 히스토리

### BR-4.4 · 커서 페이지네이션

| 항목 | 내용 |
|---|---|
| 형식 | `GET /rooms/{id}/messages?before=<seq>&limit=50` |
| 정렬 | `seq` 내림차순 |
| `before` 없음 | 최신부터 |
| `before` 있음 | 그보다 **작은** seq만 (경계 미포함) |
| `limit` 상한 | 100 |
| 근거 | FR-4.4 |

오프셋 페이지네이션을 쓰지 않는다 — 그 사이 메시지가 추가되면 경계가 밀려 중복·누락이 생긴다.

## 신고

### BR-11.1 · 발신자 본인만

| 항목 | 내용 |
|---|---|
| 조건 | `messages.sender_id != 호출자` |
| 결과 | **403** |
| 근거 | FR-11.1 |

**남의 메시지를 오발송으로 신고할 수 없다.** 이것은 "내가 잘못 보냈다"는 자기 신고이지 신고 기능이 아니다.

### BR-11.2 · 검증 상태 무관

| 항목 | 내용 |
|---|---|
| 규칙 | 6값 어느 상태의 메시지든 신고 가능 |
| 근거 | FR-11.2 |

`flagged_sent`를 제외한 다섯 상태가 사용자 판단에 대한 신호를 남기지 않는 사각지대다. 신고가 그것을 메운다.

### BR-11.3 · 취소 가능

| 항목 | 내용 |
|---|---|
| 규칙 | `misdirect_reported_at`을 NULL로 되돌린다 |
| 이력 | 남지 않는다 |
| 근거 | FR-11.1 |

## 규칙 판정 순서 — `send_message()`

```
1. BR-3.3  참여자 자격 + 토글 조회 (get_membership 1회)
2. BR-6.4  force_log_id 있으면 검증 → flagged_sent 확정
3. BR-6.1  없으면 상태 결정 (disabled / degraded / cold / 호출)
4. BR-4.3  판정 (트랜잭션 밖)
5. BR-6.3  부적절이면 409 반환하고 종료
6. BR-4.2  트랜잭션: 채번 + 저장
7. BR-4.1  커밋 후 브로드캐스트
```

## Assumptions & Open Questions

- 메시지 본문 길이 상한이 정해지지 않았다. 판정 토큰 비용과 직결된다.
- degraded 프로브 카운터가 클라이언트에 있으므로(ADR-007) 조작 가능하다. 데모 위협 모델에 없다.
- "다시 시도" 버튼이 몇 번까지 눌릴 수 있는지 제한이 없다. API가 계속 죽어 있으면 사용자가 반복해서 누를 수 있다.
- `limit` 상한 100은 이 단계에서 정한 값이다.
