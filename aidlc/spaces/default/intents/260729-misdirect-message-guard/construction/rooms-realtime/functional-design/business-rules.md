# Business Rules — rooms-realtime

`../../../inception/requirements-analysis/requirements.md`의 FR-1.3·FR-3.1~FR-3.3·FR-5.1~FR-5.4·FR-6.1·FR-10을 판정 가능한 규칙으로 편 것이다. 단위 경계는 `../../../inception/units-generation/unit-of-work.md`, 배정은 `../../../inception/units-generation/unit-of-work-story-map.md`, 컴포넌트 소유권은 `../../../inception/application-design/components.md`, 메서드 서명은 `../../../inception/application-design/component-methods.md`, 프로세스 형태는 `../../../inception/application-design/services.md`를 따른다.

## 방

### BR-3.1 · 최소 인원

| 항목 | 내용 |
|---|---|
| 트리거 | 방 생성 |
| 조건 | 초대 대상이 비어 있음 |
| 결과 | **400** `EMPTY_ROOM` |
| 근거 | FR-3.1 — 본인 포함 최소 2명 |

상한은 없다.

### BR-3.2 · 친구만 초대 가능

| 항목 | 내용 |
|---|---|
| 트리거 | 방 생성, 참여자 추가 |
| 조건 | 초대 대상 중 호출자의 친구가 아닌 id가 섞임 |
| 결과 | **400** `NOT_A_FRIEND` |
| 근거 | FR-3.1 |

**호출자 기준이다.** A가 만든 방에 A의 친구 B, C가 들어오면, B와 C는 서로 친구가 아닐 수 있다. 그것은 허용된다 — 그래서 `resolve_display_names()`에 폴백이 필요하다(U3 BR-2.8).

### BR-3.3 · 참여자만 접근

| 항목 | 내용 |
|---|---|
| 트리거 | 방 상세, 읽음 처리, 토글 변경, 히스토리, 전송 |
| 조건 | 호출자가 `room_members`에 없음 |
| 결과 | **403** `FORBIDDEN` |
| 근거 | FR-3.2, FR-3.3 |

**존재하지 않는 방도 403이다.** 404를 주면 방 id의 존재 여부가 새어나간다.

### BR-3.4 · 목록은 내 방만

| 항목 | 내용 |
|---|---|
| 트리거 | 방 목록 조회 |
| 규칙 | `room_members`에 내 행이 있는 방만. 정렬은 규정하지 않는다 |
| 빈 결과 | **200** + 빈 배열 (오류가 아니다) |
| 근거 | FR-3.2 |

## AI 검증 토글

### BR-6.1 · 개인별 적용

| 항목 | 내용 |
|---|---|
| 트리거 | 토글 변경 |
| 규칙 | **호출자 본인의** `room_members` 행만 바꾼다 |
| 결과 | 다른 참여자의 설정은 변하지 않는다 |
| 근거 | FR-6.1 |

**방장 개념이 없다.** `rooms.created_by`는 기록일 뿐 권한이 아니다.

### BR-6.2 · 신규 방 기본값

| 항목 | 내용 |
|---|---|
| 트리거 | 방 생성, 참여자 추가 |
| 규칙 | 모든 참여자의 `ai_check_enabled`를 **TRUE**로 초기화 |
| 근거 | FR-6.1 |

기본이 켜짐인 이유 — 이 앱의 존재 이유가 그 기능이다. 꺼진 채로 시작하면 아무도 안 켠다.

### BR-5.2 · 갱신 시점

| 항목 | 내용 |
|---|---|
| 트리거 | 방 입장, 그 방을 보고 있는 중 새 메시지 수신 |
| 규칙 | `last_read_seq`를 그 방의 최신 `seq`로 전진 |
| 근거 | FR-5.2 |

### BR-5.3 · 전진만 한다

| 항목 | 내용 |
|---|---|
| 조건 | 요청된 값이 현재 `last_read_seq`보다 작거나 같음 |
| 결과 | **무시**. 오류가 아니다 (200) |
| 구현 | `UPDATE ... SET last_read_seq = ? WHERE ... AND last_read_seq < ?` |
| 근거 | FR-5.2 |

**조건절이 없으면 순서가 뒤바뀐 요청이 배지를 되살린다.** 사용자가 빠르게 방을 오갈 때 실제로 일어난다.

## WebSocket

### BR-5.4 · 사용자당 연결 1개

| 항목 | 내용 |
|---|---|
| 트리거 | 새 WebSocket 인증 성공 |
| 조건 | 같은 사용자의 기존 연결이 이미 있음 |
| 결과 | 기존 연결에 `session_replaced` 프레임을 보낸 **뒤** 닫고, 새 연결로 교체 |
| 근거 | FR-5.1 |

**프레임을 먼저 보내고 닫는다.** 그냥 닫으면 밀려난 탭이 네트워크 오류로 오인해 재연결을 시도하고, 두 탭이 서로를 밀어내는 순환이 생긴다.

### BR-5.5 · 밀려난 탭의 동작

| 항목 | 내용 |
|---|---|
| 트리거 | `session_replaced` 수신 |
| 규칙 | **재연결하지 않는다.** 배너를 띄운다 |
| 배너 | "다른 탭에서 접속했습니다 — 이 탭에서 계속하려면 새로고침하세요" |
| 전송 | HTTP라서 여전히 동작한다. 다만 수신이 없으므로 배너를 유지 |
| 근거 | FR-5.1, `components.md` 다중 탭 처리 |

**전송이 HTTP인 덕분에 밀려난 탭이 반쪽은 살아 있다** (ADR-001의 부수 효과).

### BR-5.6 · 첫 프레임 인증

| 항목 | 내용 |
|---|---|
| 규칙 | 연결 직후 첫 프레임은 `{type:'auth', token}` 이어야 한다 |
| 인증 전 다른 프레임 | 처리하지 않고 `auth_error` 응답 |
| 타임아웃 | **5초** 안에 인증 프레임이 없으면 연결 종료 |
| 실패 | `auth_error` 프레임 후 종료 |
| 근거 | FR-1.3, ASM-5(5초는 이 프로젝트에서 정한 값) |

### BR-5.7 · 브로드캐스트 대상

| 항목 | 내용 |
|---|---|
| 규칙 | 방 참여자 중 **연결된 사용자에게만** 보낸다 |
| 연결 없음 | 조용히 건너뛴다 — **오류가 아니다** |
| 전송 중 소켓 사망 | 그 사용자를 unregister하고 나머지는 계속 |
| 근거 | FR-5.1 |

오프라인 사용자는 다음 입장 시 히스토리로 받는다. 미전송 큐를 만들지 않는다.

**한 소켓의 실패가 다른 참여자의 수신을 막으면 안 된다.** 루프 전체를 try로 감싸지 말고 소켓마다 감싼다.

### BR-5.8 · 본인에게도 보낸다

| 항목 | 내용 |
|---|---|
| 규칙 | 브로드캐스트 대상에 발신자를 포함한다 |
| 근거 | FR-5.1, 다중 기기 동기화 |

발신자는 HTTP 응답으로 이미 메시지를 받았지만, **다른 탭·기기의 세션도 갱신되어야 한다.** 중복은 클라이언트가 메시지 ID로 제거한다 (FR-4.3).

## 구독 순서

### BR-3.5 · 구독 먼저, 히스토리 나중

| 항목 | 내용 |
|---|---|
| 규칙 | 방 입장 시 현재 방 포인터를 **먼저** 옮기고, 그다음 히스토리를 조회한다 |
| 중복 | 메시지 ID로 제거 |
| 근거 | FR-3.3 |

**순서가 반대면 그 사이 도착한 메시지가 유실된다.** WebSocket은 이미 모든 방 메시지를 받고 있으므로 "구독"은 포인터 이동이다.

히스토리 조회 API 자체는 U5 소관이다.

## Assumptions & Open Questions

- 마지막 참여자가 나간 방을 어떻게 할지 정하지 않았다. 방과 메시지는 남는다.
- `session_replaced` 후 밀려난 탭이 HTTP로 전송할 때, 그 메시지가 새 탭에는 WebSocket으로 도착한다. 밀려난 탭 본인은 HTTP 응답으로만 본다 — 일관성 문제는 아니나 화면이 갈릴 수 있다.
- WebSocket 재연결 정책(백오프, 최대 시도)이 정해지지 않았다. `session_replaced`가 아닌 네트워크 단절에는 재연결해야 한다.
- 토스트 표시 시간과 동시 표시 개수 상한이 정해지지 않았다.
