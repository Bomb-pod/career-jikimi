# Business Rules — judgment-core

`../../../inception/requirements-analysis/requirements.md`의 FR-6.2·FR-6.3·FR-6.7·FR-7.1~FR-7.5·FR-8.1을 판정 가능한 규칙으로 편 것이다. 단위 경계는 `../../../inception/units-generation/unit-of-work.md`, 배정은 `../../../inception/units-generation/unit-of-work-story-map.md`, 컴포넌트 소유권은 `../../../inception/application-design/components.md`, 메서드 서명은 `../../../inception/application-design/component-methods.md`, 프로세스 형태는 `../../../inception/application-design/services.md`를 따른다.

## 판정 입력

### BR-6.1 · 문맥 범위

| 항목 | 내용 |
|---|---|
| 규칙 | 해당 방의 **최근 `AI_CONTEXT_N`개** 메시지 (기본 10) + 후보 문장 |
| 순서 | `seq` 오름차순 — 오래된 것이 먼저 |
| 기록 | 실제로 넣은 범위를 `context_from_seq`~`context_to_seq`에 남긴다 |
| 근거 | FR-6.2 |

문맥은 **호출자(U5)가 조회해 넘긴다.** 이 단위는 DB에서 메시지를 읽지 않는다.

`context_to_seq`는 후보 문장이 아니라 **문맥의 마지막 메시지**의 seq다. 후보는 아직 seq가 없다(저장 전이므로).

### BR-6.2 · 참여자 정보 배제

| 항목 | 내용 |
|---|---|
| 규칙 | 모델 입력에 사용자 이름·아이디·별칭·`display_name`을 넣지 않는다 |
| 허용 | 익명 화자 라벨(A, B, C…)은 넣는다 — 신원이 아니라 대화 구조다 |
| 라벨 범위 | **이 문맥 윈도우 안에서만 유효한 순번.** 같은 사람이 다른 윈도우에서 다른 라벨을 받아도 된다 |
| 근거 | FR-6.2 |

**익명 라벨을 넣는 이유** — 라벨이 없으면 모델이 대화인지 독백인지 구별하지 못한다. 화자 전환은 문맥 판단의 핵심 신호다. 윈도우 안에서만 유효한 순번이므로 신원은 새지 않는다.

### BR-6.3 · 판정 대상의 한정

| 항목 | 내용 |
|---|---|
| 규칙 | "이 방의 대화 문맥에 맞는가"만 판정한다 |
| 배제 | 욕설·비방·민감정보 등 **내용 자체의 부적절성은 판정 대상이 아니다** |
| 구현 | 프롬프트에 명시적 배제 문장을 넣는다 |
| 근거 | FR-6.7, 스코프 Q2 |

이것을 프롬프트에 안 적으면 모델이 알아서 욕설을 잡는다. 그러면 측정 대상이 둘로 늘어 precision 해석이 흐려진다.

## 판정 출력

### BR-6.4 · 모델은 점수만 반환한다

| 항목 | 내용 |
|---|---|
| 규칙 | 모델은 0.0~1.0의 **부적합 점수**만 반환한다. 적절/부적절을 말하지 않는다 |
| 강제 | Structured Outputs, `strict: true` (ADR-005) |
| 근거 | FR-6.3 |

`strict: true`가 형식을 보장하므로 **파싱 실패라는 실패 유형이 없다.** 파싱 오류를 FR-8.1의 실패 경로로 흘려보내지 않는다 — 그 경로는 네트워크·API 장애용이다.

### BR-6.5 · 임계값 판정

| 항목 | 내용 |
|---|---|
| 규칙 | `score >= AI_VERDICT_THRESHOLD` → `inappropriate`. 미만 → `appropriate` |
| 경계 | **같으면 부적절이다** (`>=`) |
| 기본값 | 0.7 |
| 기록 | 판정 당시의 임계값을 `threshold`에 남긴다 |
| 근거 | FR-6.3 |

**경계를 `>=`로 잡은 것에 실질적 의미는 없다.** 다만 정해두지 않으면 구현마다 달라지고 재현이 깨진다.

### BR-6.6 · 점수 범위 검증

| 항목 | 내용 |
|---|---|
| 조건 | 모델이 0.0~1.0 밖의 값을 반환 |
| 결과 | 0.0 또는 1.0으로 **클램프**한다. 실패로 처리하지 않는다 |
| 근거 | 요구사항에 없음 — 이 단계에서 추가한 방어 |

JSON 스키마의 `number` 타입은 범위를 강제하지 않는다. 모델이 1.2를 줄 수 있다. 실패로 처리하면 멀쩡한 판정을 버리게 되므로 클램프한다.

## 실패 처리

### BR-6.7 · 타임아웃과 재시도

| 항목 | 내용 |
|---|---|
| 타임아웃 | `AI_TIMEOUT_SECONDS` (3~5초) |
| 재시도 | **정확히 1회** |
| 총 상한 | 10초를 넘지 않는다 |
| 재시도 대상 | 타임아웃, 연결 오류, 5xx, 429 |
| 재시도 안 함 | 4xx (429 제외) — 요청 자체가 잘못된 것이라 다시 보내도 같다 |
| 결과 | 둘 다 실패하면 `JudgeResult.Failed`. **예외를 던지지 않는다** |
| 근거 | FR-8.1, NFR-1 |

**재시도가 1회인 이유** — 2회면 사용자가 최대 15초를 기다린다. 그 시점에는 이미 앱이 멈춘 것으로 읽힌다.

**실패가 예외가 아닌 이유** — 실패는 흐름의 일부다(FR-8이 degraded 경로를 정의한다). 예외로 만들면 호출자가 정상 분기를 `try/except`로 쓰게 되고, 진짜 오류와 섞인다.

### BR-6.8 · 로그는 실패해도 남긴다

| 항목 | 내용 |
|---|---|
| 규칙 | 호출을 **시도한** 모든 건에 행을 만든다. 실패면 `score`·`verdict`가 NULL |
| `latency_ms` | 실패해도 실제 대기 시간을 기록한다 |
| 근거 | FR-7.2 |

API 실패율(FR-7.5)을 세려면 실패한 시도가 남아 있어야 한다.

## 라벨과 집계

### BR-7.1 · `user_action`은 한 번만 쓰인다

| 항목 | 내용 |
|---|---|
| 조건 | `set_user_action()` 호출 시 이미 값이 있음 |
| 결과 | `AlreadyResolved` 예외 |
| 구현 | **원자적 조건부 갱신** — `UPDATE ... SET user_action=? WHERE id=? AND user_action IS NULL`, 영향받은 행이 0이면 예외 |
| 근거 | FR-7.2, `force_log_id` 1회성 |

**조건부 UPDATE가 아니라 SELECT 후 UPDATE로 짜면 1회성이 깨진다.** 두 요청이 동시에 들어오면 둘 다 SELECT에서 NULL을 보고 둘 다 UPDATE한다. 이것이 더블클릭에 메시지 두 개가 저장되는 경로다.

### BR-6.9 · `force_log_id` 검증

| 검사 | 실패 시 |
|---|---|
| 로그가 존재하는가 | `InvalidForceToken` |
| `user_id`가 호출자인가 | `Forbidden` |
| `room_id`가 이 방인가 | `InvalidForceToken` |
| `user_action`이 NULL인가 (미소진) | `InvalidForceToken` |
| **`candidate_text`가 재요청 텍스트와 일치하는가** | `InvalidForceToken` |
| `verdict`가 `inappropriate` **또는 NULL(호출 실패)** 인가 | `InvalidForceToken` |

**결과 상태는 로그의 `verdict`에서 파생된다.**

| 로그의 `verdict` | 사용자가 강행했을 때의 `verification_status` |
|---|---|
| `inappropriate` | `flagged_sent` — 경고를 보고 보냈다 |
| NULL (호출 실패) | `failed` — 검증을 시도했으나 못 받고 보냈다 |

**NULL을 허용하는 것이 FR-8.3을 성립시키는 장치다.** 판정 실패를 사용자가 수락했을 때 그 메시지는 `failed`여야 하는데(시도는 했으므로), `degraded` 플래그만 세워 재요청하면 우선순위 규칙에 걸려 `degraded`로 저장된다. `force_log_id`가 "이 시도는 이미 있었다"를 전달한다.

`verdict = 'appropriate'`인 로그는 여전히 거부한다 — 적절 판정은 이미 자동 전송되었으므로 강행할 대상이 아니다.

**텍스트 일치 검사가 `application-design`에서 이월된 미해결 항목의 해소다.** 없으면 소유자·방·미소진 조건을 만족하는 토큰에 *다른 텍스트*를 실어 판정 없이 `flagged_sent`로 통과시킬 수 있다. UI로는 도달할 수 없지만 API 직접 호출로는 가능하다.

비교는 **트림 후 정확 일치**로 한다. 정규화(공백 축약·유니코드 정규화)까지 하면 우회 여지가 생긴다.

`verdict` 검사도 추가한다 — 적절 판정 로그나 실패 로그의 id를 `force_log_id`로 쓰는 것은 의미가 없고, 막지 않으면 그 경로로 판정을 건너뛸 수 있다.

### BR-7.2 · 집계 대상

| 항목 | 내용 |
|---|---|
| 대상 | `judgment_logs` 중 **`verdict IS NOT NULL`** 인 행 |
| 제외 | `messages.verification_status`를 필터로 쓰지 않는다 |
| 근거 | FR-7.4 |

**`verification_status`로 거르면 취소된 건이 영원히 안 잡힌다** — 취소는 `messages` 행을 만들지 않기 때문이다. 그러면 TP가 항상 0이 되어 precision이 계산 불가가 된다.

### BR-7.3 · precision 계산

| 항목 | 내용 |
|---|---|
| 모집단 | `verdict = 'inappropriate'` 이고 `user_action IN ('sent','cancelled')` |
| TP | `user_action = 'cancelled'` |
| FP | `user_action = 'sent'` |
| 값 | `TP / (TP + FP)` |
| 분모 0 | `None`을 반환한다. 0으로 나누지 않고, 0.0으로도 표시하지 않는다 |
| 근거 | FR-7.3, ASM-1 |

**이 값은 근사다.** 취소가 "판정에 동의해서"인지 "귀찮아서"인지 구별하지 못한다(ASM-1). 리포트에 그 사실을 함께 출력한다.

### BR-7.4 · 미응답 건수

| 항목 | 내용 |
|---|---|
| 대상 | `verdict = 'inappropriate'` 이고 `user_action IS NULL` |
| 용도 | precision에서 제외하되 **별도 수치로 보고** |
| 해석 | 크면 팝업이 무시당하고 있다는 신호 |

### BR-7.5 · recall은 산출하지 않는다

| 항목 | 내용 |
|---|---|
| 규칙 | 리포트의 recall 항목은 수치가 아니라 **`"산출 불가 — 라벨 데이터셋 필요"`** 문자열 |
| 근거 | FR-7.5, ASM-7 |

**계산해서 0을 넣거나 항목을 빼면 안 된다.** 빼면 왜 없는지 모르고, 0을 넣으면 성능이 나쁜 것으로 오해된다. 산출 불가라는 사실 자체를 보고한다.

### BR-7.6 · 신고 데이터의 용법

| 항목 | 내용 |
|---|---|
| 규칙 | 신고 수는 비율 지표의 분모·분자로 쓰지 않는다 |
| 예외 | `신고율`(전송된 메시지 대비)은 분모가 실측이라 성립. 다만 **신고 행위의 빈도**이지 오발송 빈도가 아니다 |
| `미검출 후보` | 신고된 것 중 `verification_status='ok'`였던 **건수**. 비율이 아니라 표본 |
| 근거 | FR-7.5, ASM-6 |

## 규칙 판정 순서

`judge()` 안에서:

```
1. BR-6.1  문맥 구성 (입력 검증)
2. BR-6.2  익명화
3. BR-6.3  프롬프트 조립
4. 로그 행 생성 (score/verdict 미정)
5. BR-6.7  호출 + 타임아웃 + 재시도
      실패 --> BR-6.8 로그 갱신(NULL 유지) --> Failed 반환
6. BR-6.6  점수 클램프
7. BR-6.5  임계값 판정
8. BR-6.8  로그 갱신 (score, verdict, 토큰, latency)
9. 결과 반환
```

## Assumptions & Open Questions

- 익명 화자 라벨이 문맥 윈도우 안에서만 유효하다는 결정은 이 단계에서 내렸다. 윈도우가 밀릴 때마다 같은 사람의 라벨이 바뀌는데, 그것이 판정 품질에 영향을 주는지 확인되지 않았다.
- `AI_TIMEOUT_SECONDS`의 구체적 기본값(3인지 5인지)이 정해지지 않았다. 총 상한 10초를 지키려면 4 이하여야 한다.
- 429(rate limit)를 재시도 대상에 넣었으나 `Retry-After`를 존중할지 정하지 않았다. 존중하면 총 상한 10초를 넘길 수 있다.
- precision의 분모가 0일 때 `None`을 반환하기로 했으나, 리포트에서 그것을 어떻게 표시할지 정하지 않았다.
