# Business Rules — auth-friends

`../../../inception/requirements-analysis/requirements.md`의 FR-1.1~FR-1.3·FR-2.1~FR-2.4를 판정 가능한 규칙으로 편 것이다. 단위 경계는 `../../../inception/units-generation/unit-of-work.md`, 배정은 `../../../inception/units-generation/unit-of-work-story-map.md`, 컴포넌트 소유권은 `../../../inception/application-design/components.md`, 메서드 서명은 `../../../inception/application-design/component-methods.md`, 배포 형태는 `../../../inception/application-design/services.md`를 따른다.

각 규칙은 위반 시의 응답까지 정한다. 응답 코드가 정해지지 않은 규칙은 규칙이 아니다.

## 인증

### BR-1.1 · 아이디 유일성

| 항목 | 내용 |
|---|---|
| 트리거 | 회원가입 요청 |
| 조건 | 같은 `username`이 이미 존재 |
| 결과 | **409** `USERNAME_TAKEN`. 계정 생성 안 함 |
| 근거 | FR-1.1 |

경쟁 조건은 DB의 UNIQUE 제약이 막는다. 애플리케이션의 사전 조회는 편의일 뿐이며, **INSERT의 무결성 위반도 반드시 409로 변환해야 한다.** 두 요청이 동시에 들어오면 사전 조회는 둘 다 통과한다.

### BR-1.2 · 비밀번호 최소 길이

| 항목 | 내용 |
|---|---|
| 트리거 | 회원가입 요청 |
| 조건 | 비밀번호가 8자 미만 |
| 결과 | **400** `WEAK_PASSWORD`. 계정 생성 안 함 |
| 근거 | FR-1.1, ASM-5(8자는 이 프로젝트에서 정한 값) |

상한은 두지 않는다. bcrypt는 72바이트를 넘으면 잘라내므로, **72바이트 초과 입력은 잘린다는 사실을 알고 있어야 한다** — argon2를 쓰면 이 제약이 없다.

### BR-1.3 · 비밀번호 저장 형태

| 항목 | 내용 |
|---|---|
| 트리거 | 계정 생성, 비밀번호 검증 |
| 규칙 | 저장은 bcrypt 또는 argon2 해시만. 평문·역가능 암호화 금지 |
| 결과 | 위반은 코드 결함이며 런타임 규칙이 아니다 |
| 근거 | FR-1.1, NFR-6 |

### BR-1.4 · 로그인 실패 응답의 동일성

| 항목 | 내용 |
|---|---|
| 트리거 | 로그인 요청 |
| 조건 | 아이디가 없거나 비밀번호가 틀림 |
| 결과 | **401** `INVALID_CREDENTIALS` — **두 경우를 구분하지 않는다** |
| 근거 | FR-1.2 |

"그런 아이디 없음"과 "비밀번호 틀림"을 구분하면 계정 존재 여부가 새어나간다. 응답 본문도 응답 시간도 같아야 한다.

**응답 시간까지 같게 하려면** 아이디가 없을 때도 더미 해시로 검증을 한 번 돌려야 한다. 데모 범위에서 필수는 아니나, 하지 않기로 했다면 그 사실을 알고 하지 않는 것이다.

### BR-1.5 · 토큰 검증

| 항목 | 내용 |
|---|---|
| 트리거 | 보호된 엔드포인트 접근, WebSocket 첫 프레임 |
| 조건 | 서명 불일치, 만료, 형식 오류, 존재하지 않는 사용자 |
| 결과 | HTTP는 **401**. WebSocket은 `auth_error` 프레임 후 연결 종료 |
| 근거 | FR-1.2, FR-1.3 |

`verify_token()`은 **동기 순수 함수**여야 한다 — HTTP 의존성 주입에 묶이면 WebSocket 경로에서 재사용할 수 없다.

토큰이 가리키는 사용자가 삭제된 경우는 이 프로젝트에 없다(탈퇴 없음). 그래도 조회 실패를 401로 다룬다.

### BR-1.6 · 비밀 주입 경로

| 항목 | 내용 |
|---|---|
| 규칙 | JWT 서명 키는 `core/config`(U1)를 통해서만 읽는다 |
| 결과 | 소스에 리터럴로 존재하면 결함 |
| 근거 | FR-1.4(U1 소유), NFR-6 |

## 친구

### BR-2.1 · 정확 일치 검색

| 항목 | 내용 |
|---|---|
| 트리거 | 사용자 검색 |
| 규칙 | `username`이 **정확히** 일치하는 한 명만 반환. 부분 일치·대소문자 무시·유사도 검색 없음 |
| 결과 | 없으면 빈 결과(404가 아니다 — 검색은 성공했고 결과가 없을 뿐) |
| 근거 | FR-2.1 |

MariaDB의 기본 콜레이션(`utf8mb4_unicode_ci`)은 **대소문자를 구분하지 않는다.** `Alice`로 검색해도 `alice`가 나온다. 이것을 정확 일치로 볼지 결정해야 한다 — 아래 열린 항목 참조.

### BR-2.2 · 별칭 필수

| 항목 | 내용 |
|---|---|
| 트리거 | 친구 등록, 별칭 수정 |
| 조건 | 별칭이 없거나, 빈 문자열이거나, **트림 후 빈 문자열** |
| 결과 | **400** `ALIAS_REQUIRED`. 등록·수정 안 함. 수정의 경우 기존 값 유지 |
| 근거 | FR-2.2, FR-2.3 |

**트림 후 검사가 핵심이다.** DB의 NOT NULL은 `"   "`를 막지 못한다.

저장 시에도 트림한 값을 넣는다 — 앞뒤 공백이 표시를 흔든다.

### BR-2.3 · 단방향 등록

| 항목 | 내용 |
|---|---|
| 트리거 | 친구 등록 |
| 규칙 | `owner_id`의 목록에만 추가. 상대의 목록은 변하지 않는다. 승인 절차 없음 |
| 근거 | FR-2.2 |

### BR-2.4 · 중복 등록 금지

| 항목 | 내용 |
|---|---|
| 트리거 | 친구 등록 |
| 조건 | `(owner_id, friend_id)`가 이미 존재 |
| 결과 | **409** `ALREADY_FRIEND` |
| 근거 | FR-2.2, 엔티티 UNIQUE 제약 |

BR-1.1과 같이 DB 제약이 최종 방어선이며 무결성 위반을 409로 변환한다.

### BR-2.5 · 자기 자신 등록 금지

| 항목 | 내용 |
|---|---|
| 트리거 | 친구 등록 |
| 조건 | `friend_id == owner_id` |
| 결과 | **400** `CANNOT_FRIEND_SELF` |
| 근거 | 요구사항에 없음 — 이 단계에서 추가한 상식 제약 |

### BR-2.6 · 존재하지 않는 대상

| 항목 | 내용 |
|---|---|
| 트리거 | 친구 등록 |
| 조건 | `username`에 해당하는 사용자가 없음 |
| 결과 | **404** `USER_NOT_FOUND` |
| 근거 | FR-2.2 |

검색(BR-2.1)은 빈 결과를 주지만 등록은 404를 준다. **의도적으로 다르다** — 검색은 "찾아봤다"이고 등록은 "이 대상에 대해 작업하라"이기 때문이다.

### BR-2.7 · 별칭 수정 권한

| 항목 | 내용 |
|---|---|
| 트리거 | 별칭 수정 |
| 조건 | 대상 `friendship.owner_id != 호출자` |
| 결과 | **403** `FORBIDDEN` |
| 근거 | FR-2.3 |

존재하지 않는 `friendship_id`도 403으로 응답한다 — 404를 주면 남의 friendship id 존재 여부가 새어나간다.

### BR-2.8 · 표시명 해석

| 항목 | 내용 |
|---|---|
| 트리거 | 친구 목록, 방 참여자 표시, 히스토리 발신자 표시 |
| 규칙 | 호출자가 그 사용자를 친구로 등록했으면 **별칭**. 아니면 그 사용자의 `display_name` |
| 근거 | FR-2.4, `component-methods.md`의 열린 항목 |

**친구 목록에서는 폴백이 절대 일어나지 않는다** — 목록에 있다는 것 자체가 친구라는 뜻이고, 별칭은 NOT NULL이기 때문이다. 폴백은 방 참여자와 히스토리에서만 발생한다(다른 사람이 초대한 참여자, FR-10.1).

## 규칙 간 우선순위

한 요청에 여러 규칙이 걸리면 **싼 검사부터** 판정한다.

친구 등록의 경우:

```
1. BR-2.2 별칭 검사      (입력만 보면 됨, DB 접근 없음)
2. BR-2.6 대상 존재      (조회 1회)
3. BR-2.5 자기 자신      (조회 결과로 판정)
4. BR-2.4 중복           (조회 1회 또는 INSERT 무결성 위반)
```

여러 규칙을 동시에 위반해도 **첫 번째 위반만 응답한다.** 필드별 오류 목록을 만들지 않는다 — 입력이 두세 개뿐이라 값어치가 없다.

## Assumptions & Open Questions

- **대소문자 구분**: MariaDB 기본 콜레이션이 대소문자를 무시하므로 `Alice`와 `alice`가 같은 사용자로 취급된다. FR-2.1의 "정확 일치"가 이것을 허용하는지 명시되지 않았다. 데모에서는 허용하는 편이 사용자에게 친절하나, 아이디 유일성(BR-1.1)도 같은 콜레이션을 따르므로 `Alice`와 `alice`가 동시에 가입할 수 없다는 뜻이기도 하다. 일관되므로 그대로 둔다.
- **타이밍 공격 방어**: BR-1.4의 응답 시간 균일화를 구현할지 정하지 않았다. 데모 위협 모델에는 없다.
- **`display_name` 초기값**: 회원가입 시 별도 입력을 받을지 `username`을 복사할지 미정.
- **비밀번호 상한**: bcrypt의 72바이트 절단을 그대로 둘지 argon2로 피할지 미정. Code Generation에서 라이브러리를 고를 때 정한다.
