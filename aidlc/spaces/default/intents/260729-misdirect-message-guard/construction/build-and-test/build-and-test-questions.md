## Q1 — `starlette` 취약점 8건을 지금 잡는가

`pip-audit`이 23건을 찾았다. 그중 고칠 수 있는 것은 이미 고쳤다:

| 패키지 | 조치 | 결과 |
|---|---|---|
| `PyJWT` 2.10.1 → **2.13.0** | 올림 | 11건 해소. **314 테스트 전부 통과**, API 변경 없음 |
| `asyncmy` 0.2.10 → **0.2.11** | 올림 | PYSEC-2026-286은 최신에도 있고 **수정 버전이 공개되지 않았다.** 올려도 안 없어진다 |
| `pytest` 8.3.4 | 조치 안 함 | 개발 전용. **런타임 이미지에 안 들어간다** |
| **`starlette` 0.41.3** | **미정 — 이 질문** | 8건. 수정은 `>= 1.3.1` |

`starlette`는 직접 의존성이 아니라 `fastapi`가 끌어온다. 올리려면 **fastapi 0.115.6 → 0.141.1** (마이너 26개 점프)이 필요하다.

**실제로 해봤다:**

- `starlette 1.3.1`까지 올라가고 8건이 전부 사라진다
- **테스트 2개가 깨진다** — `test_ws_auth.py`의 라우트 등록 확인 2건. starlette 1.x가 라우트 객체에서 `.path`를 노출하지 않는다. 나머지 312개는 통과
- 깨진 둘은 단언만 하는 테스트라 고치는 것 자체는 작다. **문제는 그것이 아니라, 26개 버전 사이의 동작 변화 중 우리 테스트가 안 덮는 부분이다**

판단 재료:

- 이 앱은 **로컬 데모다.** `requirements.md` § Out of Scope가 원격 배포를 명시적으로 범위 밖에 두었다. `docker-compose.yml`은 `localhost:8000`만 노출하고 db는 호스트에 열지 않는다
- starlette 권고들은 HTTP 계층에 닿는 **원격 공격자**를 전제한다
- 최종 발표가 **08-04**, 오늘이 07-30이다
- 되돌리기는 쉽다 — 핀 두 줄

- A. **지금은 두고 기록한다 (추천)** — 로컬 전용이라 도달 경로가 없다. 수용된 위험으로 `security-test-instructions.md`에 근거와 함께 남기고, 원격 배포를 하게 되면 그때 **첫 번째로** 처리한다. 발표까지 안정성을 지킨다
- B. **지금 올린다** — fastapi 0.141.1 + starlette 1.3.1. 깨진 테스트 2개를 고치고 전체를 다시 돌린다. 8건이 사라지지만 발표 4일 전에 웹 프레임워크를 26버전 올린다
- C. 다른 방법 (예: starlette만 강제 핀 — fastapi가 지원하지 않아 깨질 가능성이 높다)
- X. Other (please specify)
