# Scope Definition & Prioritization — Questions

**Stage**: scope-definition
**Phase**: IDEATION
**Depth**: Standard
**Mode**: self-guided (사용자가 파일 직접 편집; 모드 전환)

## 입력

`../intent-capture/intent-statement.md`에서 이미 확정된 것 — 여기서 다시 묻지 않는다:

- 핵심 문제 = 채팅방 착각 오발송, 전송 전 차단
- 우선 지표 = precision (recall은 측정하되 우선순위 아님)
- 노력 배분 = 판정 경로 집중, 회원가입·친구·방 생성 축소
- AI 검증 토글 = 참여자 개인 단위
- 친구 별칭 = 필수 입력 + 사후 수정 가능
- 제품 경계 = 로컬 채팅 웹앱 데모 하나 (데이터셋 구축·성능 테스트는 제외)
- 일정 = 착수 07-29, 중간 점검 07-31, 최종 발표 08-04
- 구현 = 본인 전담

아래 질문은 그 위에서 **무엇을 자를지**를 정한다. `intent-statement.md`가 남긴 가정 중 2번(내용 필터링 배제 여부)과 14번(별칭 필수 vs 껍데기 축소 충돌)이 여기서 닫힌다.

## Q3. 별칭 필수 입력과 "친구 등록은 껍데기로 최소화"가 충돌한다. 어떻게 조정하는가?

> Intent Capture에서 둘 다 확정되었다 — 노력 배분은 친구 등록 흐름을 줄이라고 하고, 별칭은 그 흐름에 필수 입력과 수정 기능을 더한다.
>
> 실제 비용은 크지 않다: `friendships.alias` NOT NULL 컬럼 하나, 등록 폼의 입력칸 하나, 수정용 PATCH 엔드포인트 하나. 다만 "최소화"의 기준선을 명시해두지 않으면 뒤 단계에서 다시 흔들린다.

- A. 별칭은 유지하되 친구 기능의 나머지를 최소화 — 검색은 아이디 정확 일치만, 승인 절차 없이 즉시 등록, 목록은 정렬·검색 없음
- B. 별칭도 최소화 — 등록 시 필수 입력만 받고 수정 기능은 시간이 남으면 만든다
- C. 충돌 아님 — 별칭 포함해서 친구 기능을 제대로 만든다
- D. Not yet defined
- X. Other (please specify)

[Answer]: A

## Q5. AI 검증 **실패 처리**를 어디까지 만드는가?

> `README.md`에 정교한 설계가 있다: 타임아웃 3~5초, 재시도 1회, 첫 실패 시 사용자에게 한 번 묻고 승낙하면 degraded 전환, degraded 중 5번째 메시지마다 프로브로 회복 감지, 검증 안 된 메시지에 배지.
>
> 이건 판정 경로의 일부라 노력 배분상 우선순위가 높다. 다만 프로브 회복 감지까지 만들면 상태 관리가 눈에 띄게 복잡해진다.

- A. 전부 만든다 — 타임아웃·재시도·degraded·프로브 회복·배지까지
- B. 프로브 회복만 제외 — 타임아웃·재시도·degraded 전환·배지까지. 회복은 새로고침으로
- C. degraded 전체 제외 — 실패하면 그때마다 "검증 실패, 그래도 보낼까요?"를 묻는다
- D. 최소 — 실패하면 검증 없이 보내고 배지만 단다. 묻지 않는다
- E. Not yet defined

- C. 세션 쿠키 — WebSocket 인증이 단순해진다
- D. Not yet defined
- X. Other (please specify)

[Answer]:A

## Q8. (후속 — 모순 해소) Q4=C가 앞 단계의 노력 배분 결정과 반대 방향이다.

> 이번 Q3=A에서도 친구 기능의 나머지를 최소화하기로 했다.
> 그런데 Q4=C는 `README.md`가 "우선순위 최하 (시간 남으면)"으로 분류한 두 기능(채팅방 참여자 추가, 채팅방 나가기)을 확정 범위로 승격한다.
>
> 친구 기능은 줄이면서 방 기능은 늘리는 셈이라, 방침이 일관되지 않다. 두 기능 자체는 각각 크지 않지만(참여자 추가는 방 멤버 INSERT + 초대 UI, 나가기는 DELETE + 목록 갱신 + 남은 인원 처리), 승격의 근거가 무엇인지에 따라 뒤 단계의 우선순위 판단이 달라진다.

- A. Q4를 A로 정정 — 둘 다 이번 범위에서 제외하고 백로그에 "Won't have (this time)"으로 남긴다
- B. Q4를 B로 정정 — 방 나가기만 포함, 참여자 추가는 제외
- C. C 유지 — 노력 배분 축소 방침은 인증·친구에만 적용하고 방 기능은 예외로 둔다. 시연에서 방을 정리하거나 참여자를 늘리는 장면이 필요하다
- D. C 유지하되 순위를 낮춘다 — 범위에는 넣되 Must가 아닌 Should로 두어, 일정이 밀리면 가장 먼저 잘린다
- X. Other (please specify)

## Q9. (후속 — 범위 대 일정) 7/31과 8/4의 범위를 나눌 것인가?

> Q1=B는 이틀 뒤 중간 점검에 AI 검증 팝업까지 동작하기를 요구하고, Q5=A는 실패 처리 전체(타임아웃·재시도 1회·degraded 전환·5번째 메시지 프로브 회복·미검증 배지)를 요구한다. 여기에 Q6=A(JWT+해싱)와 Q4의 방 기능, 그리고 `(room_id, seq)` 채번·낙관적 렌더링·구독 순서 보장이 더해진다.
>
> Q5=A를 포기하자는 것이 아니다. **언제까지**를 나누면 둘 다 살릴 수 있다. 이 답은 Delivery 단계의 Bolt 순서에 직접 반영된다.

- A. 나눈다 — 7/31까지는 전송→판정→팝업의 핵심 경로 + 실패 시 단순 폴백(검증 없이 전송 + 배지). degraded 전환·프로브 회복은 8/4까지 얹는다
- B. 나누지 않는다 — 7/31까지 Q1=B와 Q5=A를 모두 밀어붙인다
- C. 더 보수적으로 — 7/31까지는 AI 없는 채팅만(Q1의 A), AI 검증 전체를 8/4까지
- D. 나누되 경계가 다르다 (X에 기재)
- X. Other (please specify)

[Answer]: B. 나누지 않는다 — 7/31까지 Q1=B와 Q5=A를 모두 밀어붙인다

## Q10. (후속 — 신규 범위) "도커 배포"의 범위는 어디까지인가?

> 사용자 요청: "도커 배포까지 하도록 하자." 승인 게이트에서 제기되어 `scope-document.md`의 경계를 수정했다.
>
> 범위에 따라 워크플로 계획이 달라진다. 원격 배포까지 가면 건너뛴 environment-provisioning·deployment-execution 단계를 되살려야 하고, 도메인·HTTPS·비밀 관리가 따라붙는다.

- A. 로컬 컨테이너화 — 백엔드·프론트 Dockerfile + docker-compose(앱 + MariaDB). `docker compose up` 한 번으로 전체 기동
- B. 원격 서버에 실제 배포 — 클라우드나 원격 호스트에 올려 외부 접속 가능하게
- C. 이미지 레지스트리 푸시까지 — Docker Hub / GHCR
- D. 로컬 컨테이너화 + 원격은 Should로
- X. Other (please specify)

[Answer]: A. 로컬 컨테이너화 — 백엔드·프론트 Dockerfile + docker-compose(앱 + MariaDB). `docker compose up` 한 번으로 전체 기동
