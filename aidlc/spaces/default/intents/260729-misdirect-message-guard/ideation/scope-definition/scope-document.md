# Scope Document — 문맥 기반 오발송 메시지 경고

## 입력과 근거

이 문서는 `../intent-capture/intent-statement.md`의 확정 사항 위에 세워진다. 그 문서가 정한 것 — 핵심 문제(채팅방 착각 오발송의 전송 전 차단), 우선 지표(precision), 노력 배분(판정 경로 집중), AI 검증 토글의 개인 단위 적용, 별칭 필수 입력, 제품 경계(로컬 채팅 웹앱 데모 하나), 일정(착수 07-29 / 중간 점검 07-31 / 최종 발표 08-04), 본인 전담 구현 — 은 여기서 다시 열지 않는다.

이 문서가 새로 정하는 것은 **경계**다. 무엇을 만들고, 무엇을 만들지 않으며, 무엇이 먼저인가.

`intent-statement.md`가 남긴 가정 중 두 건이 여기서 닫혔다.

| intent-statement 가정 | 해소 |
|---|---|
| 내용 기준 필터링이 범위 밖이라는 확정이 없다 | **범위 밖으로 확정** (Q2) |
| 별칭 필수와 껍데기 축소가 반대 방향으로 당긴다 | **별칭은 유지, 친구 기능의 나머지를 최소화** (Q3) |

## Scope Boundary

### 만드는 것 — Must

| 영역 | 포함 내용 |
|---|---|
| 인증 | 회원가입·로그인, 비밀번호 해싱(bcrypt/argon2), JWT 발급·검증, WebSocket 연결 직후 첫 프레임 auth |
| 친구 | 아이디 **정확 일치** 검색, 승인 절차 없는 즉시 등록, **별칭 필수 입력**, 별칭 수정 |
| 채팅방 | 친구 다수 선택 초대로 방 생성, 방 목록, 방 입장 |
| 메시지 | 저장 먼저·브로드캐스트 나중, `(room_id, seq)` 채번, 실시간 전송, 낙관적 렌더링 후 ack ID 교체, `before=<seq>` 커서 히스토리, 구독 먼저·히스토리 fetch 나중 |
| AI 검증 | 개인별 토글(신규 방 기본 켜짐), 최근 N개 문맥으로 적절/부적절 판정, 부적절 시 전송 확인 팝업, 문맥 부족 시 콜드스타트 스킵 |
| 실패 처리 | 타임아웃 3~5초, 재시도 1회, 첫 실패 시 1회 확인 후 degraded 전환(사용자 전역·세션 단위), degraded 중 5번째 메시지마다 프로브 회복 감지 + 회복 알림, 미검증 배지 |
| 데이터 | 6값 `verification_status`(`ok` / `flagged_sent` / `disabled` / `skipped_no_context` / `failed` / `degraded`), 별도 판정 로그 테이블 |
| 컨테이너화 | 백엔드·프론트엔드 Dockerfile, `docker-compose.yml`(앱 + MariaDB), DB healthcheck 후 앱 기동, 환경변수로 비밀 주입. `docker compose up` 한 번으로 전체 기동 |

### 만드는 것 — Should

일정이 밀리면 **가장 먼저 잘리는** 항목이다. 범위 안에 있지만 Must가 아니다.

| 항목 | 비고 |
|---|---|
| 채팅방 참여자 추가 | 시연에서 방에 사람을 늘리는 장면이 필요할 수 있다 |
| 채팅방 나가기 | 시연 중 방을 정리할 때 쓸모가 있다 |

`README.md`는 이 둘을 "우선순위 최하 (시간 남으면)"으로 두었다. Should 등급은 그 취지를 유지하면서, 잘라낼 때 근거를 남긴다.

### 만들지 않는 것 — Won't have (this time)

| 항목 | 이유 |
|---|---|
| 내용 기준 필터링 (욕설·비방·민감정보) | 판정은 "이 방의 문맥에 맞는가"만 본다. 측정 대상을 하나로 유지해야 precision 해석이 흐려지지 않는다 (Q2) |
| 데이터셋 구축 (트랙 2) | 제품 경계 밖. 이번 산출물은 웹앱 데모 하나다 |
| 성능 테스트 (트랙 3) | 같은 이유. 이번에 만드는 것은 측정 **도구**(판정 로그)이지 측정 자체가 아니다 |
| 타이핑 인디케이터, 읽음 표시, 파일·이미지 전송 | 판정 성능과 무관하고 구현 비용만 든다 |
| 원격 서버 배포·CI 파이프라인·이미지 레지스트리 푸시·관측성·인시던트 대응 | 컨테이너화는 범위에 있지만 **로컬까지**다 (Q10). 클라우드 호스트, 도메인, HTTPS, 비밀 관리 서비스, 이미지 레지스트리는 범위 밖이며 활성 스코프도 OPERATION 전 단계를 건너뛴다 |
| 상대가 설정한 이름 표시 | 별칭이 필수가 되면서 fallback 경로 자체가 사라졌다 |
| 친구 목록 정렬·검색, 친구 승인 절차 | "친구 기능의 나머지를 최소화" 결정에 따른다 (Q3) |

## Prioritization — MoSCoW

| 등급 | 항목 | 판단 근거 |
|---|---|---|
| **Must** | 메시지 저장·문맥 조회·판정 로그 | 노력 배분이 이쪽에 집중된다. 측정의 대상 |
| **Must** | AI 검증 판정 + 부적절 팝업 | 이 프로젝트의 존재 이유 |
| **Must** | 실시간 전송 (WebSocket) | 판정을 보여줄 무대. 없으면 판정도 보여줄 수 없다 |
| **Must** | 실패 처리 전체 (degraded·프로브 포함) | Q5=A. 검증받았다고 믿는 사용자를 조용히 배신하지 않기 위한 경로 |
| **Must** | 인증 (JWT + 해싱) | 사용자 구분이 없으면 방도 친구도 성립하지 않는다. 하드코딩 금지 규칙도 걸려 있다 |
| **Must** | 친구 등록 + 별칭 | 방을 만들려면 친구가 필요하다. 별칭은 명시적 요청 |
| **Must** | 방 생성·목록·입장 | 판정의 단위가 방이다 |
| **Must** | 컨테이너화 (Dockerfile + compose) | Q10. MariaDB는 어차피 compose가 필요했다. 앱까지 넣으면 발표 시연이 환경에 의존하지 않는다 |
| **Should** | 참여자 추가, 방 나가기 | Q8=D. 일정 압박 시 첫 절단 대상 |
| **Won't** | 위 "만들지 않는 것" 전체 | — |

Must가 많다. 이 프로젝트에서 "판정을 보여준다"는 목표는 인증부터 실시간 전송까지의 사슬 전체가 이어져야 성립하기 때문이고, 그 사슬 중 하나라도 빠지면 데모가 서지 않는다. 대신 각 Must의 **깊이**를 얕게 가져간다 — 친구 검색은 정확 일치만, 방 목록은 정렬 없이, 인증은 리프레시 토큰 없이.

## Value Stream

사용자 가치가 흐르는 경로다. 굵은 구간이 이 프로젝트가 값어치를 만드는 곳이다.

```
[가입/로그인] -> [친구 등록] -> [방 생성] -> [방 입장]
                                                |
                                                v
                                        [이전 대화 로드]
                                                |
                                                v
   +--------------------------------------------------------+
   |  **[메시지 입력] -> [문맥 N개 조회] -> [LLM 판정]**      |
   |            |                              |             |
   |         적절 |                     부적절 |             |
   |            v                              v             |
   |     **[저장 -> 브로드캐스트]**   **[확인 팝업]**         |
   |                                     |        |          |
   |                                 보내기      취소        |
   |                                     |        |          |
   |                                     v        v          |
   |                        **[flagged_sent]** **[로그만]**  |
   +--------------------------------------------------------+
                                |
                                v
                        **[판정 로그 적재]**
```

왼쪽 구간(가입·친구·방)은 **껍데기**다. 오른쪽 굵은 구간이 측정 대상이며, 노력 배분이 그쪽으로 간다.

취소된 메시지가 `messages`에 남지 않고 판정 로그에만 남는다는 점이 중요하다 — 그 로그의 `user_action`이 사실상의 정답 라벨 역할을 한다.

## Sequencing

**빌드 순서 기준: 위험 우선** (Q7).

활성 스코프가 `skeleton: on`이므로 첫 Bolt는 종단 간 얇은 수직 슬라이스로 돌고 사용자 승인을 받는다. 위험 우선 기준에서 이 프로젝트의 불확실성이 큰 곳은 두 군데다.

1. **WebSocket 실시간 전송** — 단일 연결 멀티플렉싱, 연결 레지스트리, 구독·fetch 순서, `(room_id, seq)` 채번의 동시성
2. **LLM 판정** — 응답 지연, 프롬프트 설계, 판정 품질

두 위험을 모두 관통하는 얇은 슬라이스가 walking skeleton이 된다: 로그인(스텁 수준) → 방 하나 → 메시지 한 건 → 저장·브로드캐스트 → 판정 → 로그 적재. 구체적인 Bolt 분할은 Units Generation과 Functional Design에서 확정한다.

**컨테이너화는 walking skeleton에 포함한다 — 마지막이 아니라 처음이다.** 컨테이너를 나중에 붙이면 그동안 쌓인 환경 의존(로컬에만 있는 파이썬 버전, 호스트에 깔린 DB, 하드코딩된 접속 문자열)이 한꺼번에 드러나고, 그 시점은 대개 발표 직전이다. 처음부터 컨테이너 안에서 돌리면 그 부채가 쌓이지 않는다. 비용도 초기가 더 싸다 — 테이블 하나, 엔드포인트 하나일 때의 compose 파일이 가장 단순하다.

## Assumptions & Open Questions

- 문맥 메시지 개수 `N`의 값이 아직 정해지지 않았다. `README.md`는 10~20을 제안하나 실험 변수로 남아 있다.
- 판정 프롬프트 설계가 정해지지 않았다. Application Design 또는 Functional Design에서 다룬다.
- 판정 성능 집계의 정답 라벨 기준이 미확정 상태로 남아 있다 (`intent-statement.md`에서 이월).
- 프로젝트명이 정해지지 않았다.
- Should 항목을 실제로 잘라낼 판단 시점이 정해지지 않았다. Delivery 관점에서는 walking skeleton Bolt 완료 시점이 자연스러운 결정 지점이다.
