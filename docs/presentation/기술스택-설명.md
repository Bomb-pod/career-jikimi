# 기술스택 설명 — career-jikimi

발표자료 슬라이드 6 "아키텍처 / 기술스택" 카드의 각 기술이 무엇이고,
이 프로젝트에서 어떤 역할을 하는지 정리한 문서. Q&A 대비용.

---

## 프론트엔드

| 기술 | 설명 | 이 프로젝트에서의 역할 |
|---|---|---|
| **React 18** | 컴포넌트 기반 UI 라이브러리 | 방 목록, 채팅창, 경고 팝업이 전부 React 컴포넌트 |
| **TypeScript 5.7** | JavaScript에 정적 타입을 붙인 언어 | 메시지·방·판정 응답의 구조를 타입으로 고정해 실수를 컴파일 시점에 잡음 |
| **Vite 6** | 개발 서버 + 번들러 | 수정 즉시 반영(HMR), 배포용 정적 파일(`dist/`)을 만들어 nginx가 서빙 |
| **Zustand** | 경량 상태 관리 라이브러리 (Redux의 가벼운 대안) | 방 목록·메시지·판정 팝업 상태를 `chatStore.ts` 하나로 관리 |

## 백엔드

| 기술 | 설명 | 이 프로젝트에서의 역할 |
|---|---|---|
| **FastAPI** | Python 비동기 웹 프레임워크 | 회원가입/로그인/방/메시지 API + WebSocket 엔드포인트. async라 판정 대기 중에도 다른 요청 처리 |
| **WebSocket** | 연결을 계속 열어두는 양방향 통신 프로토콜 | 실시간 메시지 송수신. **사용자당 1개 연결로 여러 방을 멀티플렉싱** — 메시지마다 `room_id`를 달아 한 통로로 오가고, 방을 옮겨도 연결을 새로 열지 않음 |
| **SQLAlchemy** | Python ORM | SQL 대신 Python 클래스(`JudgmentLog` 등)로 DB를 다룸. 비동기 드라이버 `asyncmy`와 함께 사용 |
| **Alembic** | DB 마이그레이션 도구 | 테이블 구조 변경 이력을 코드로 관리 — 팀원 전원이 같은 스키마를 재현 |

## 데이터

| 기술 | 설명 | 이 프로젝트에서의 역할 |
|---|---|---|
| **MariaDB (InnoDB)** | MySQL 계열 관계형 DB. InnoDB는 트랜잭션·행 잠금을 지원하는 저장 엔진 | 메시지 `seq` 채번을 `SELECT ... FOR UPDATE`로 처리 — 행 잠금이라 **방 단위로만 직렬화**되고 다른 방 전송은 막지 않음 |
| **utf8mb4 명시 지정** | 4바이트 유니코드 문자셋 | 기본값으로 두면 한글·이모지가 깨질 수 있어 **명시적으로** 지정 (README 설계 결정) |

## Q&A 대비 — "왜 그걸 썼나"

| 예상 질문 | 답 |
|---|---|
| 왜 MariaDB인가 | utf8mb4·InnoDB 행 잠금(seq 채번)이 필요했고, 팀에 친숙한 MySQL 계열 |
| 왜 Zustand인가 | Redux보다 보일러플레이트가 적고 이 규모에는 충분 |
| 왜 CPU 추론인가 | 0.1B 소형 모델이라 GPU 없이 538ms면 충분 — 배포 서버에 GPU를 요구하지 않게 됨 |
| 왜 WebSocket 연결이 1개인가 | 방 개수만큼 연결이 늘어나는 비용을 피하고, 안 보고 있는 방의 메시지도 실시간 수신. 대가는 연결 레지스트리가 프로세스 메모리에 있어 수평 확장 불가 → Redis pub/sub이 고도화 과제 |
| 왜 FastAPI인가 | async 기반이라 판정(수백 ms) 대기 중에도 다른 요청을 막지 않음. WebSocket 지원 내장 |
