두 가지 기동 방식이 공존한다 · 같은 compose 프로젝트 · 같은 DB 볼륨 · 2026-08-03

1두 가지 기동 방식

기존 구성을 대체하지 않는다. 같은 프로젝트의 두 가지 기동 방식으로 공존한다. 둘 다 name:을 두지 않아 compose가 디렉터리 이름(mini_project)을 프로젝트 이름으로 쓰고, 그래서 DB 볼륨과 네트워크를 그대로 공유한다. 겹쳐도 문제가 없는 이유는 애초에 동시에 뜨지 못하기 때문이다 — 같은 서비스 이름을 정의하므로 한쪽을 올리면 다른 쪽이 다시 만들어진다. 

# 분리 구성으로  → http://localhost
cd frontend && npm run build && cd ..
docker compose -f compose.nginx.yml up --build

# 기본 구성으로 되돌리기
docker compose up -d --remove-orphans      # --remove-orphans 로 web 컨테이너를 치운다

2nginx 분리 구성 상세

백엔드 코드는 한 줄도 바뀌지 않았다. _mount_spa()가 static/이 없으면 조용히 건너뛰도록 이미 되어 있어서, 정적 파일만 빼면 자동으로 API 전용 서버가 된다. 원래 Vite dev 서버를 위해 넣은 분기가 그대로 여기에 맞았다.

3라우팅 규칙과 검증 결과

실제 nginx 1.24에 스텁 백엔드를 붙여 요청을 하나씩 넣어 확인했다. `/api` 접두사를 만들지 않는다 — components.md가 엔드포인트를 접두사 없이 확정했고, 여기서 새로 만들면 개발과 배포의 경로가 갈라진다.

경계가 핵심이다 정규식이 (/|$)로 경계를 요구하기 때문에 /rooms/12는 API로, /rooms-not-api·/healthcheck는 SPA로 간다. 이게 없으면 /roomsomething이 백엔드로 샌다.
WS 타임아웃 60초 → 3600초 이 앱은 타이핑 인디케이터도 읽음 표시도 없어(범위 밖) 대화가 없으면 프레임이 전혀 오가지 않는다. 기본값이면 1분 뒤 조용히 끊기고, 재연결 전 도착한 메시지를 놓친다.
목록이 두 곳에 있다 nginx.conf와 vite.config.ts의 BACKEND_PATHS. 새 최상위 라우터가 생기면 둘 다 고쳐야 한다. 빠뜨리면 JSON 자리에 <!doctype html>이 온다.

4메시지 전송 · 판정 플로우

nginx는 이 흐름을 바꾸지 않는다. 요청을 app으로 넘기는 한 홉이 앞에 붙을 뿐이다. 원칙도 그대로다 — 저장 먼저, 브로드캐스트 나중(순서가 반대면 DB 쓰기 실패 시 화면엔 보이는데 새로고침하면 사라진다), 그리고 실패해도 조용히 보내지 않는다(사용자는 검증받았다고 믿고 있다).

nginx로도 워커는 못 늘린다 ws_registry가 프로세스 메모리에 있어 app 인스턴스를 늘리면 로드밸런싱이 오히려 문제를 만든다 (CON-1). upstream에 서버를 더 적으면 WebSocket이 갈라진다. Redis pub/sub이 먼저다.
CORS는 여전히 필요 없다 nginx가 정적과 API를 같은 오리진으로 묶기 때문이다. .env의 CORS_ORIGINS는 비워둘 것. 정적을 별도 도메인(S3/CDN)에 올리는 방식이었다면 그때는 필수가 된다.
원격 배포로 가면 여기가 이득 TLS 종단, starlette 취약점 8건의 “로컬 전용이라 도달 경로 없음” 전제가 깨지는 시점의 필터링 지점, /docs 접근 제어 — 셋이 한꺼번에 풀린다.
