3메시지 전송 · 판정 흐름

이 프로젝트의 심장이다. 원칙은 저장 먼저, 브로드캐스트 나중 — 순서가 반대면 DB 쓰기가 실패했을 때 화면엔 보이는데 새로고침하면 사라진다.

1
클라이언트 — 낙관적 렌더링
Enter → 임시 ID로 말풍선을 먼저 그린다. 동시에 전송 버튼을 비활성화하고 "확인 중…"을 띄운다. 판정 대기가 1~3초라 표시가 없으면 앱이 멈춘 줄 안다.
2
서버 — 검증할 것인가
room_members.ai_check_enabled는 참여자 개인별 설정이다. 방장이 켠다고 전원에게 적용되지 않는다 — "내가 실수하는 걸 막는" 기능이므로 남이 내 전송 지연을 결정하면 안 된다.
토글 꺼짐
판정 없이 전송
disabled
문맥 < N
콜드 스타트, 건너뜀
skipped_no_context
켜짐 + 문맥 충분
아래 3번으로
3
judgment.judge() — 문맥 조립 → 익명화 → 모델 호출
최근 N개(10~20) 메시지 + 지금 보내려는 문장. 참여자 정보는 쓰지 않는다 — 순수하게 대화 문맥만 본다. 실제로 넣은 범위를 context_from_seq/context_to_seq로 남겨 재현 가능하게 한다. 타임아웃 4초, 재시도 1회만 (2회면 사용자가 9초를 기다린다).
4
결과 분기
Appropriate
seq 채번(SELECT … FOR UPDATE) → INSERT → 방 참여자 브로드캐스트 → ack
verification_status = ok
Inappropriate
409 Blocked, 저장하지 않는다. 팝업 "이 방에 맞지 않는 것 같습니다"
→ 강행 시 force token으로 flagged_sent
→ 취소 시 메시지는 안 남고 로그만 남는다
Failed
조용히 보내지 않는다. 첫 실패에 한 번만 물어보고, 수락하면 degraded로 전환
5번째 메시지마다 프로브로 회복 감지
5
judgment_logs 기록
verdict · confidence · threshold · latency_ms · prompt_tokens / completion_tokens · user_action(sent / cancelled). 마지막 항목이 사실상의 정답 라벨이라 실사용 로그가 그대로 평가 데이터가 된다.
정렬은 created_at이 아니라 (room_id, seq). 채번은 한 트랜잭션 안에서 SELECT last_seq … FOR UPDATE → +1 → INSERT. InnoDB 행 잠금이라 방 단위로만 직렬화되고 다른 방의 전송은 막지 않는다. 방 입장 순서도 구독 먼저, 히스토리 나중 — 반대로 하면 그 사이 도착한 메시지가 유실된다.

4판정 백엔드 교체

.env의 JUDGMENT_BACKEND 한 줄로 갈아끼운다. 코드 변경이 없다 — 셋 다 같은 ModelCall을 돌려주므로 판정 로직·로그·강행 전송·지표가 그대로다.

openai
기본값. OpenAI API 호출.
  • 키 필요
  • 최근 N개 메시지가 외부로 나감 → 사용자에게 고지
  • 토큰 비용 추적
ollama
로컬 LLM (Qwen 등).
  • 키 불필요
  • OpenAI 호환 엔드포인트라 client.py 같은 코드 경로
  • base_url·모델명만 다름
encoder ← 현재
파인튜닝 인코더. 외부 전송 없음.
  • A.X-Encoder-base(ModernBERT) 파인튜닝
  • torch 지연 import — 다른 백엔드에선 없어도 앱이 뜬다
  • 299MB 로딩이 느려 lifespan에서 warmup
임계값은 백엔드가 정하지 않는다. judge()는 settings.AI_VERDICT_THRESHOLD 하나만 본다 — 그래야 judgment_logs.threshold가 설정값과 같다는 불변식(BR-6.5)이 지켜져 나중에 판정을 재현할 수 있다. 모델 폴더의 threshold.json은 경고용으로만 읽는다. 두 값이 0.02 넘게 어긋나면 warmup()이 로그로 경고한다 — 인코더로 바꾸면서 임계값을 안 고치는 것이 가장 흔한 실수이기 때문이다.

5데이터 모델

판정 로그를 처음부터 별도 테이블로 두었다. 성능 측정이 목적인데 메시지 테이블만 있으면 실험 데이터가 쌓이지 않고, 사용자가 취소한 건은 메시지로 남지도 않는다.

  • display_name
friendships
  • owner_id → users
  • friend_id → users
  • alias (필수, 수정 가능)
  • 단방향 · 승인 없음

  • id · title
  • last_seq ← 채번 대상
room_members

  • ai_check_enabled 개인별, 신규 기본 켜짐
messages
  • room_id · seq ← 정렬 키
  • sender_id · body · created_at
  • verification_status 6종
judgment_logs
  • message_id nullable — 취소 건은 없음
  • context_from_seq · context_to_seq
  • verdict · confidence · threshold
  • latency_ms · prompt/completion_tokens
  • user_action sent / cancelled

messages.verification_status — 6개 값을 합치지 않는 이유가 각각 있다.

값의미
ok검증 통과 · 성능 집계 대상
flagged_sent부적절 판정, 사용자가 전송 강행 · 성능 집계 대상
disabled검증 토글이 꺼진 방
skipped_no_context문맥 부족(콜드 스타트). 판단 자체가 불가능
failed검증을 시도했으나 에러·타임아웃
degraded사용자 동의하에 검증을 아예 건너뜀

failed와 degraded를 합치면 "API가 얼마나 자주 실패했나"를 셀 때 degraded 구간이 섞여 장애 빈도가 과대 집계된다. 성능 집계는 ok + flagged_sent만 쓴다.

평가에서 precision이 우선 지표다. false positive가 치명적이다 — 멀쩡한 메시지에 팝업이 계속 뜨면 아무도 못 쓴다. 다만 50:50 평가셋의 precision은 실사용보다 낙관적이므로 기저율 보정을 같이 봐야 하고, FP가 0이어도 FPR이 0인 것은 아니다(0/n의 95% 상한은 약 3/n).
