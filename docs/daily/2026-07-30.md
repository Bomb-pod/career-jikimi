## 오늘의 핵심 — 테스트가 잡은 결함 넷

전부 **손으로는 안 보이는 것들**이었다. 이게 오늘 얻은 가장 큰 값어치다.

### 1. MariaDB 1020 — 순차 테스트는 전부 초록이었다

InnoDB는 트랜잭션의 read view가 잡힌 뒤 갱신된 행에 잠금 읽기가 닿으면
`1020 Record has changed since last read`를 낸다. MySQL은 최신 커밋본을 그냥 준다.

`send_message()`의 1~5단계(참여자 확인·문맥 조회·판정)가 read view를 잡아버려서
**첫 번째 이후의 동시 전송이 전부 실패**했다. 채번 트랜잭션을 새 read view로
시작하게 고쳤고, 이건 설계 문서의 6단계 `BEGIN` 위치가 원래 뜻하던 바이기도 하다.

> **NFR-7이 "동시 채번"을 명시 테스트 의무로 지목해두지 않았다면 데모 중에 발견했을 것이다.**
> `asyncio.gather` + 별도 커넥션 + 실제 커밋이 아니면 재현되지 않는다.

### 2. WebSocket 교체가 새 연결을 지웠다

```
탭 A 연결 → register(1, A)
탭 B 연결 → register(1, B) → A에 session_replaced 후 닫음
A의 핸들러가 깨어나 finally → unregister(1)   ← 여기서 B가 지워진다
```

id만 보고 지우면 방금 붙은 B가 사라지고, B는 자기가 등록됐다고 믿은 채 아무것도
못 받는다. `unregister(user_id, ws)`로 소켓 동일성을 확인하게 했다.

### 3. 멈춘 탭 하나가 새 접속을 10초 막았다 — 라이브에서만 나왔다

| 밀려난 탭 | 새 탭의 `auth_ok`까지 |
|---|---|
| close에 응답 (정상 브라우저) | **0.0초** |
| 응답 안 함 (멈춘 탭·끊긴 네트워크) | **10.0초** |

`await existing.close()`가 close 핸드셰이크 완료를 기다린다. 레지스트리는 이미
교체됐고 프레임도 나간 뒤라 기다릴 이유가 없다. 1초 상한 → **1.00초**.

> **단위 테스트가 못 잡은 이유** — 가짜 소켓의 `close()`가 즉시 반환한다.
> 실패 모드가 실제 전송 계층에만 있었다. 컨테이너를 띄워 raw 소켓으로
> 두드리는 층위를 둔 값어치가 여기서 나왔다.

### 4. `.env`만 고쳐서는 되돌아가는 설정 결함

"타임아웃 4초로" 답을 `.env` 두 파일에만 반영하고 `config.py`의 필드 기본값은
5.0으로 뒀다. 리뷰어가 `Settings(_env_file=None)`으로 **그 기본값이 실제 런타임
경로임을 증명**했다 — CI·k8s처럼 환경변수를 직접 주입하는 배포에서는 거기가 유일한
출처이고, `env_file: required: true`는 파일 존재만 확인하지 키 존재는 확인하지 않는다.

수정 테스트는 `== 4.0`이 아니라 `MAX_ATTEMPTS × 기본값 < TOTAL_BUDGET_SECONDS`
**부등식**으로 짰다. 숫자로 박으면 다음 사람이 값을 바꾸며 테스트도 함께 고쳐
불변식이 사라진다.

## 내일 첫 할 일 — 하나뿐이다

`.env`의 `OPENAI_API_KEY`가 아직 `PLACEHOLDER-...`다.

```bash
docker compose exec app python -m app.judgment.try \
  --context "내일 회의 몇 시죠?" "10시입니다" "자료는 제가 준비할게요" \
  --candidate "오늘 저녁에 치킨 어때?"
```

**채팅 UI도 방도 사용자도 필요 없다.** `judgment-core`를 DAG에서 앞으로 당긴
값어치가 정확히 여기다 — 키만 넣으면 점수·판정·지연·토큰이 바로 나온다.

확인할 것 셋:

1. **프롬프트가 실제로 문맥 부적합을 잡는가** — 이 프로젝트의 가장 큰 미지수
2. **NFR-1 실측** — 정상 5초 / 최악 10초 안에 드는가
3. **점수 구간 설명이 분포를 벌리는가** — 안 벌리면 0.5 근처로 몰린다

셋 다 **검증되지 않은 가정**이며, 셋 다 이 명령 하나로 관찰이 시작된다.

## 데이터셋·파인튜닝

`dataset/`(744행 라벨)과 `training/`(A.X-Encoder 파이프라인)이 저장소에 들어왔다.
요구사항이 트랙 2로 분류해 이번 범위 밖에 둔 작업이다.

**발표에서 쓸 수 있는 지점** — FR-7.5는 "recall은 산출 불가, 라벨 데이터셋 필요"라고
못박았다. 라이브 로그로는 놓친 오발송의 모수를 알 수 없기 때문이다. 이 데이터셋이
있으면 **오프라인 평가로 recall을 낼 수 있다.** 라이브 지표의 한계는 그대로지만
"측정 못 함"이 아니라 "라이브로는 못 재고 오프라인으로는 이렇게 쟀다"로 말할 수 있다.
