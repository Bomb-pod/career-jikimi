## 오늘 발견한 큰 문제 셋

### 1. recall은 측정할 수 없다

**질문에서 나왔다** — "API로 판별하는 거면 성능 지표는 어떻게 도출해?"

구조적 비대칭이 있다. 사용자 피드백은 **모델이 부적절이라 한 건에서만** 나온다(팝업이 뜨니까). 적절 판정된 메시지는 조용히 전송되고 아무 신호도 안 남긴다. 그래서 **놓친 오발송(FN)의 모수를 알 수 없다.**

`intent-statement`에 recall을 "측정하되 우선순위 아님"으로 적었던 것은 이 사실을 모른 채 쓴 것이다.

**대응**: `FR-7.5`에 산출 가능/불가 지표를 명시하고, FN 신호를 얻기 위해 **오발송 신고 버튼(FR-11)** 을 신설했다. 리포트의 recall 항목은 수치가 아니라 `"산출 불가 — 라벨 데이터셋 필요"` 문자열이다.

**precision 우선이 옳았던 진짜 이유가 여기 있다** — 취향이 아니라 라이브에서 측정 가능한 게 그것뿐이다.

### 2. precision이 영원히 0으로 계산될 뻔했다

리뷰어가 잡았다. 취소된 판정은 `messages` 행이 없어 `verification_status`도 없는데, 집계를 그 컬럼으로 필터링하고 있었다. **취소 = TP인데 TP가 항상 0**이 되는 구조였다.

**대응**: 집계 축을 `messages`에서 **판정 로그**로 옮겼다. `verdict IS NOT NULL`인 행만 쓴다.

### 3. 판정 실패 수락 경로가 자기모순이었다

리뷰어가 잡았다. 판정 실패를 수락한 메시지는 `failed`여야 하는데(시도는 했으니까), `degraded` 플래그로 재요청하면 우선순위 규칙에 걸려 `degraded`로 저장되고 있었다. **NFR-7 테스트 대상에 그 전이를 넣어뒀으니, 그대로 구현했으면 내가 쓴 테스트가 내 설계를 실패시켰을 것이다.**

**대응**: `force_log_id`를 실패 로그에도 허용했다. 그 토큰의 의미가 원래 "판정 시도가 있었고 사용자가 결정했다"라 실패 케이스에도 맞는다. 결과적으로 부적절 판정과 판정 실패가 **같은 재요청 경로**를 쓰게 되어 설계가 오히려 단순해졌다.

## 판정 프롬프트

`judgment-core/functional-design/business-logic-model.md`에 전문이 있다. 두 문장이 실질적으로 중요하다.

> **"메시지 내용 자체의 적절성은 판단하지 마십시오"**
> 없으면 모델이 욕설까지 잡아 측정 대상이 둘로 늘고 precision 해석이 흐려진다.

> **"화제가 바뀌었다는 사실만으로 부적합하다고 보지 마십시오"**
> 없으면 화제 전환을 전부 잡아 flag rate가 치솟고, 팝업이 무시당하기 시작하면 기능이 죽는다.

문맥은 화자를 **윈도우 내 순번(A, B, C)** 으로 익명화해 넣는다. 라벨이 없으면 모델이 대화를 독백으로 읽는다. 순번은 그 판정에만 유효하므로 신원은 새지 않는다.

## 작업 단위와 순서

```
        foundation (M)
         /          \
judgment-core (L)  auth-friends (M)
         \              |
          \      rooms-realtime (L)
           \          /
            messaging (XL)
```

**`judgment-core`를 앞으로 당긴 것이 이 분해의 핵심이다.** 의존 행렬상 `config`·`db` 외에 아무것도 의존하지 않아 **채팅 UI 없이 CLI로 판정 품질을 확인할 수 있다.**

설계에 `try` CLI를 넣어뒀다:

```bash
python -m app.judgment.try \
  --context "내일 회의 몇 시죠?" "10시입니다" "자료는 제가 준비할게요" \
  --candidate "오늘 저녁에 치킨 어때?"
```

프롬프트를 고치고 바로 다시 돌릴 수 있다.

## 내일 첫 결정 — 미해결

**"프론트를 먼저 구현해달라"** 고 하셨는데, 단위가 백엔드+프론트로 묶여 있어 순서를 정해야 한다. 여기서 멈췄다.

| 안 | 내용 | 트레이드오프 |
|---|---|---|
| **B (추천)** | 백엔드 엔드포인트를 하드코딩 응답으로 30분 만에 세우고, 그 위에 프론트 | 계약이 처음부터 실물이라 갈아끼울 일이 없다 |
| A | 목(mock) `apiClient`로 화면을 먼저 완성 | 화면이 가장 빨리 나오지만, 갈아끼울 때 계약 불일치가 몰려서 터진다 — 그날이 발표 전날이 되기 쉽다 |
| C | DAG 순서 그대로 | 가장 큰 미지수를 먼저 확인하지만 화면이 늦다 |

**순서와 무관하게 `judgment-core`는 일찍 건드리는 게 낫다.** 프롬프트가 기대만큼 안 나오면 프로젝트 전체가 흔들리는데, 화면을 다 만든 뒤에 알면 손쓸 시간이 없다. 화면 작업 중간중간 `try` CLI로 돌려보는 정도면 된다.
