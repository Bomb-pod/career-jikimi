## 오늘의 핵심 — 배포 임계값이 0.99였다

`.env`에 `AI_VERDICT_THRESHOLD=0.7`을 적어두었지만 **적용되지 않고 있었다.**

```
우선순위: ENCODER_THRESHOLD → threshold.json → AI_VERDICT_THRESHOLD
.env 에 ENCODER_THRESHOLD 없음  →  threshold.json 의 0.99 가 이긴다
```

`threshold.json`이 담고 있던 값:

```json
"threshold": 0.99, "oof_precision": 1.0, "oof_recall": 0.034, "oof_flag_rate": 0.017
```

**recall 0.034.** 오발송 100건 중 3건만 잡고 팝업률이 1.7%다. 기능이 사실상 뜨지
않는 상태였고, 이대로 데모했으면 경고창을 한 번도 못 보여줬을 수 있다.

### 왜 0.99가 저장됐나

노트북 §9의 폴백이다. `TARGET_PRECISION = 0.95`를 만족하는 지점이 학습 데이터
OOF에 없어(최대 0.933) `max(cands, key=precision)`으로 빠졌고, 그 지점이 스윕
끝쪽인 0.99였다.

**학습 데이터에서 뽑은 임계값을 난이도가 다른 데이터에 그대로 옮긴 것**이 원인이다.
학습 데이터는 응답만으로 못 맞히게 설계돼 어렵고, 평가셋은 두 집단이 0.687 벌어져
있을 만큼 쉽다.

### 조치

`.env`에 한 줄. 재빌드 불필요(`env_file`은 런타임 로드).

```
ENCODER_THRESHOLD=0.7
```

`threshold.json`은 수정하지 않는다 — `max_len` 384를 어댑터가 실제로 읽어 쓰고,
학습 시점 기록(epochs 4, 1000행)이 재현에 필요하다.

> **교훈** — 설정이 여러 곳에서 오면 우선순위를 문서에만 적어두면 안 된다.
> 기동 로그에 실제 적용값을 찍게 해둔 것이 이번에 확인 경로가 됐다.

## 학습 곡선 — EPOCHS 4가 맞았다

`train_one_fold`는 epoch별 **학습 loss만** 남기고 검증은 끝나고 한 번만 한다.
과적합 진단 곡선을 그릴 재료가 없어, 학습 루프 안에서 **25스텝마다** 검증셋을
재는 계측 전용 노트북을 따로 만들었다 (`AX_Encoder_학습곡선.ipynb`).

16 epoch · 1600스텝 · 검증 64회 · 25분.

```
검증 loss 최저   : epoch  4.00   loss 0.3582   acc 0.870   하락폭 +0.420
검증 정확도 정점 : epoch  5.25   acc 0.900
[과적합 확인] 최저점 이후 검증 loss가 +0.3783 올라간다
```

**행 수 기반 자동 분기가 고른 4가 실제 최적점이었다.** 감으로 정한 게 아니라
계측으로 확인했다는 근거가 생겼다.

### 곡선에서 새로 보인 것 셋

**초반 2 epoch은 거의 안 배운다.** 검증 정확도 0.510 → 0.575. warmup이
`int(1600 × 0.1) = 160스텝 = 1.6 epoch`이라 그전까지 학습률이 낮다. 2.0 → 2.75에서
0.575 → 0.850으로 급점프하는 것이 warmup 종료 직후다.

**문맥 사용은 아주 일찍 확립된다.** 하락폭이 epoch 2.25에 이미 +0.300이다.
"성능이 먼저 오르고 나중에 문맥을 배운" 게 아니라 처음부터 문맥으로 배웠다.

**과적합이 문맥 포기로 오지 않았다.** 16 epoch까지 하락폭 +0.42가 유지된다.
보통 과적합이 오면 모델이 쉬운 단서(응답 표면)로 갈아타는데 그러지 않았다.
학습 loss는 epoch 7에 0.0008로 완전히 외운 뒤에도 그렇다.

> epoch 7 이후 9 epoch은 낭비였다. 다시 잴 일이 있으면 `PROBE_EPOCHS = 8`로 충분하다.

적절해 보인다.

데이터를 보면 짐작이 간다. hard 셋의 두 라벨은 거의 쌍둥이 문장이고(평균 25.7자
대 25.3자), 부적절 쪽이 더 단정적이다.

```
적절   기존 API는 유지하고 관리자 조회 API를 추가하겠습니다.
부적절 기존 API를 삭제하고 새 API로 교체하겠습니다.
```

**문맥이 없으면 단정적인 쪽이 더 좋은 업무 답변처럼 보인다.** 다만 점수가 전부
0.001~0.03에 뭉쳐 있어 실용적 영향은 없다 — 어느 쪽이든 팝업이 안 뜨는 영역이다.

> recall 0.020은 threshold 문제가 아니다. 0.05까지 내려도 0.060이다.
> 부적절 항목의 점수 중앙값이 0.0078이라 어디에 선을 그어도 안 걸린다.

## 수치 출처 통일 — OOF 기준으로 확정

재구성 과정에서 **덱의 숫자가 두 출처에서 섞여 들어올 뻔했다.** 학습 1,000행
5-fold OOF와 독립 평가셋 100행은 난이도가 달라 값이 다르다.

| | 학습 1,000행 OOF | 평가셋 100행 |
|---|---|---|
| 정확도 | 0.854 | 1.000 |
| 절제 하락 | −0.385 (정확도) | −0.362 (AUC) / −0.450 (정확도) |
| 기저율 1% precision | 0.07 | 0.14 |

**OOF 기준으로 통일하고 각 장에 출처를 각주로 달았다.**

이유는 임계값이다. 0.7의 근거인 threshold sweep이 학습 데이터 OOF에서 나왔으므로
임계값 장은 어차피 OOF여야 논리가 맞다. 평가셋 쪽을 대표로 쓰면 AUC 1.000 / FP 0건이
전면에 나오는데, 이건 "100행이라 그런 것 아니냐"는 질문을 자초한다.

- 절제 실험 장(13) — **0.854 / 0.469 / 0.485, 하락폭 −0.385**. 각주에 평가셋
  재현 결과(AUC −0.362 · 정확도 −0.450)를 방향 확인용으로만 병기
- 기준선·임계값 장(14) — 전부 OOF. 각주에 "임계값 sweep도 같은 데이터"
- 평가 방법론 장(12) — 각주에 "두 종류를 쓰되 한 장 안에서 섞지 않는다"를 명시
- 기저율 1% precision — **0.14**로 통일 (평가셋 오탐 0건의 95% 상한 0.06 적용)
- 지연 — 대표 수치를 **단일 요청 p50 538ms**로. 배치 32 처리량 512ms는 각주

> **원칙 하나** — 한 장 안에서 두 출처를 섞지 않는다.
> 섞으면 질문 한 번에 무너진다.

스크립트에 예상 질문 "발표의 숫자는 어느 데이터 기준인가요?"를 추가해뒀다.
07-31의 OOF 불일치(보고서 0.832 vs 노트북 0.854)는 **여전히 미해결**이다.
덱은 노트북 기준 0.854로 통일하고 13장 노트에 Q&A 대비 문구를 넣었다.
