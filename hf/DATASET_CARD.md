# career-jikimi 문맥 적절성 데이터셋

**채팅방을 착각해 잘못 보낸 메시지**를 판별하기 위한 한국어 이진 분류 데이터셋.

`(대화 문맥, 보내려는 메시지) → 적절 / 부적절`

## 구성

| 파일 | 행 | 용도 |
|---|---|---|
| `training_dataset_v3_1000.csv` | 1,000 (500/500) | 학습 |
| `test_dataset_100.csv` | 100 (50/50) | 평가 |
| `test_dataset_100_hard.csv` | 100 (50/50) | 평가 (범위 밖 대조군) |

### 컬럼

| | |
|---|---|
| `pair_id` | 짝 식별자. **분할은 반드시 이 단위로 한다** |
| `history` | 대화 문맥. `화자: 발화` 줄바꿈 구분 |
| `response` | 보내려는 메시지 |
| `label` | `적절` / `부적절` |
| `turn_count` | 문맥 턴 수 |
| `source`, `source_type`, `difficulty` | 학습셋에만. 슬라이스 분석용 |
| `reason`, `reason_detail` | `test_dataset_100_hard`에만. 부적절 유형 |

## 데이터 오염 통제

**평가 100행은 학습 1,000행에 포함되어 있지 않다.**

| 검사 | `test_dataset_100` | `test_dataset_100_hard` |
|---|---|---|
| `(history, response)` 완전 일치 | 0 / 100 | 0 / 100 |
| `response`만 일치 | 0 / 100 | 0 / 100 |
| `history`만 일치 | 0 / 100 | 0 / 100 |

## 설계 — 응답 표면에 정답이 새지 않게

이 데이터셋의 핵심은 **짝 구조**다.

**고유 응답 500개가 각각 적절 1회 + 부적절 1회로 등장한다.** 같은 문장이 맞는
방에서는 적절, 어긋난 방에서는 부적절이다. 그래서 **응답만 보고는 원리적으로
맞힐 수 없고**, 문맥을 봐야만 풀린다.

| | 학습셋 v3 | 초기본(폐기) |
|---|---|---|
| response만으로 맞히기 | **0.400** | 0.992 |
| history만으로 맞히기 | 0.264 | 0.694 |
| 양쪽 라벨에 등장하는 응답 | **500 / 500** | 0 |

초기본은 부적절이 전부 잡담체, 적절이 전부 화제 관련이라 **응답 문체만 외우면
99%가 맞는** 데이터였다. 그것으로 학습하면 "문맥 이해"가 아니라 "문체 분류"를
배운다. 짝 구조로 재조립해 그 지름길을 없앴다.

> **주의 — 평가셋에는 짝 구조가 없다.** `test_dataset_100`은 응답만으로 0.840이
> 맞는다. 학습셋보다 쉬운 데이터이므로, 여기서 나온 정확도를 일반 성능으로
> 읽으면 안 된다. 문맥 사용 여부는 절제 실험(문맥 교체 후 재측정)으로 봐야 한다.

## `test_dataset_100_hard` — 범위 밖 대조군

**이 셋은 "더 어려운 오발송"이 아니라 다른 종류의 문제다.** 부적절 50건의 유형:

| `reason` | 건수 | 정의 |
|---|---|---|
| N4 | 40 | 명시된 조건·제한사항 위반 |
| N3 | 4 | 요청의 핵심을 처리하지 않음 |
| N1 | 4 | 시간·순서·대상이 문맥과 불일치 |
| N2 | 2 | 이전 발화를 잘못 해석 |

예시(N4):

> history: "기존 API는 **유지**하고 관리자 조회 API만 추가해주세요"
> response: "기존 API를 **삭제**하고 새 API로 교체하겠습니다"

**같은 방·같은 주제다.** 방을 착각한 게 아니라 지시를 잘못 따랐다.
오발송 탐지 모델의 성능을 이 셋으로 재면 낮게 나오는 것이 정상이며,
**범위를 벗어난 입력에서 오탐을 내지 않는지** 확인하는 용도로 쓰는 것이 맞다.

## 사용 시 주의

**1. 분할은 `pair_id` 그룹 단위로.** 같은 응답을 공유하는 두 행이 학습·검증에
갈라지면 검증 점수가 부풀려진다.

```python
from sklearn.model_selection import StratifiedGroupKFold
cv = StratifiedGroupKFold(5, shuffle=True, random_state=42)
cv.split(df, y, groups=df["pair_id"])
```

**2. 화자 호칭을 익명화할 것.** `history`는 `팀장:` `선임:` 같은 실제 호칭을
쓴다(66종). 서비스가 화자 정보를 모델에 넘기지 않는다면, 학습 전에 **등장
순서대로 A/B/C로 치환**해 형식을 맞춰야 한다. 실측에서 검증 성능이
0.855 → 0.890으로 올랐다 — 호칭이 암기 손잡이로 쓰이고 있었다.

**3. `source`·`difficulty`를 입력으로 쓰지 말 것.** 슬라이스별 성능을 나눠
보고하는 용도다.

## 만든 방식

한국어 대화 시나리오를 사람이 설계하고, 각 방에 맞는 응답과 어긋난 응답을
짝으로 붙였다. 카톡체·축약 표현이 포함되어 있으나 **AI 모사이므로 실제 사용자
분포와 다를 수 있다.**

`difficulty=hard` 구간은 같은 도메인·같은 말투에 **인명과 일정만 어긋나게** 만든
쌍이다(앱TF↔서버TF, 마케팅↔채용 등). 단순 유사도로는 가릴 수 없다.

## 한계

- 문맥 다양성 제한. 긴 문맥(10턴 이상)은 약 10%다.
- 부적절 예시가 전부 **다른 방 문맥과 결합한 형태**다. 같은 방 안에서 날짜·대상만
  어긋난 경우는 없다 — `test_dataset_100_hard`의 N1이 그 빈틈을 보여준다.
- 실제 사용자 로그가 아니다. 최종 검증은 실사용 데이터로 해야 한다.
