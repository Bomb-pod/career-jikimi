# 문맥 적절성 데이터셋 v2 (짝 구조 재조립)

> career-jikimi의 '방 착각 탐지' 태스크용. v1(`dialogue_appropriateness_dataset_500_final.csv`)을
> 재조립해 **같은 response가 history에 따라 적절/부적절 양쪽에 등장하는 짝(counterfactual) 구조**로 만들었다.

## 1. v1을 그대로 쓸 수 없었던 이유

v1은 TF-IDF + 로지스틱 회귀만으로 **response만 보고 99.2%** 를 맞힐 수 있었고,
**history를 무작위로 섞어도 성능이 떨어지지 않았다**(0.944). 원인은 두 층:

1. **템플릿 종결문** — N1의 종결문이 50행에 10종뿐("그러고 보니 그 얘기를 하려고 했어" 등).
   문구만 보고 label을 맞힐 수 있었다.
2. **화제 분포 분리** — 부적절은 전부 사적 잡담, 적절은 전부 공감체·업무체.
   종결문을 지워도 어휘만으로 90.7%가 나왔다.

이대로 파인튜닝하면 문맥 판정기가 아니라 **말투 분류기**가 된다. 게다가 "사적 잡담 = 부적절"을
학습하므로, 친구방의 정상 잡담마다 팝업이 뜬다 — 프로젝트가 가장 경계하는 false positive를
데이터에서부터 심는 셈이다.

또한 N2(감정 축소)·N4(공격)·N5(갈등 확대)·N3(질문 무시) 200행은 **내용/화용 문제**로,
프로젝트의 닫힌 결정("내용 기준 필터링 배제") 밖이다. → 별도 파일로 분리 보존했다.

## 2. v2 구성 (520행, 적절 260 / 부적절 260)

핵심 원칙: **모든 고유 response(260개)는 적절 1회 + 부적절 1회씩 등장한다.**
→ response만 봐서는 정확히 50%. label을 맞히려면 history와의 관계를 읽어야만 한다.

| source_type | 행수 | label | 구성 방법 |
|---|---|---|---|
| `matched` | 250 | 적절 | v1 적절(P1~P5) 원본 짝 그대로 |
| `cross_scenario` | 230 | 부적절 | matched의 response에 **다른 시나리오 그룹**의 history를 1:1 결합 |
| `work_to_casual` | 20 | 부적절 | 업무 response × 신규 일상 잡담 history — "회사 메시지를 친구방에" |
| `smalltalk_casual` | 10 | 적절 | N1 잡담(첫 문장만) × 일상 잡담 history — "잡담방에서 잡담은 정상" |
| `smalltalk_serious` | 10 | 부적절 | 같은 잡담 × 진지한 history — "잡담을 업무방에" |

세부 규칙:

- **cross_scenario 결합 제약**: 시나리오 그룹(emotional={갈등, 고민·감정 상담} / task={업무, 질문·요청,
  정보 공유} / casual={일상}) 이 서로 다를 것 + TF-IDF 유사도 < 0.25 + 가능하면 격식(존댓말/반말) 일치.
  같은 그룹 내 결합(예: 고민 상담 응답 → 갈등 history)은 우연히 적절할 수 있어 금지했다.
- **N1 잡담은 첫 문장만** 사용 — 뒷문장에 원본 문맥 참조("아무튼 발표 얘기는 나중에 하자")가 남아
  잡담방 짝의 라벨을 오염시키기 때문. 중복 제거 후 고유 잡담은 10개다(v1 N1 50행의 실체).
- **N1 원본 history는 미사용** — 15/50이 일상 대화라서 "잡담방에서 잡담=적절" 기준과 모순된다.
  잡담의 부적절 짝은 matched에서 예약한 진지한 P history를 썼다(이 history들도 적절 1회+부적절 1회로 균형).
- **신규 일상 잡담 history 20종**을 새로 작성(반말, 마지막 화자는 상대방, 직접 질문으로 끝나지 않음).
  라벨 양쪽에 나눠 써서(부적절 20 : 적절 10) history 측 누출을 최소화했다.

**본 태스크에서는 사용하지 않는다.** 향후 "톤 경고" 확장 기능을 만들 때를 위한 보존이다.
단, v1의 템플릿 종결문 문제는 이 파일에 그대로 남아 있으므로 사용 전 같은 검증을 거칠 것.

## 3. 검증 결과 (`validate_context_dataset.py`)

TF-IDF(char 2-4gram) + 로지스틱 회귀, 5-fold 그룹 CV:

| 검사 | v1 | v2 | 통과 기준 |
|---|---|---|---|
| response-only | **0.992** | **0.500** | ≤ 0.55 |
| history-only | 0.694 | 0.513 | ≤ 0.55 |
| history 셔플 + concat | 0.944 | 0.527 | ≤ 0.60 |
| 관계 특징(유사도+격식 불일치) | 0.660 | **0.677** | 단독 특징보다 높을 것 |

v2에서 표면 특징은 전부 우연 수준이고, history-response **관계** 특징만 유의하게 남았다.
어휘 중첩+격식 불일치만으로 0.68이므로, 의미를 읽는 cross-encoder 파인튜닝의 목표는
**이 0.68을 크게 넘는 것**이다. (참고: concat 검사가 0.5보다 낮게 나오는 것은 짝 구조에서
표면 암기가 역효과를 내기 때문 — 표면 특징이 오히려 해가 된다는 추가 증거다.)

**데이터셋을 수정할 때마다 이 스크립트를 다시 실행할 것.** 결측치·중복·분포 균형보다
이 검증이 중요하다. 실패하는 데이터셋은 문맥을 측정하지 않는다.

## 4. 학습 시 반드시 지킬 것

1. **분할은 `pair_id` 단위로.** 쌍둥이 행이 train/test에 갈라지면 암기가 평가를 오염시킨다.
   (`StratifiedGroupKFold(groups=pair_id)`)
2. 모델 입력은 `history + response`만. `persona`/`scenario`는 입력에 넣지 않는다
   (프로젝트 결정: "참여자 정보는 사용하지 않는다").
3. 지표는 precision 우선, `source_type`별 오류 분석 병행.
4. 500~520행 규모이므로 여러 seed 반복 + k-fold로 분산 확인.

## 5. 한계 (v3에서 개선할 것)

- **cross_scenario 230행은 자동 생성** — 유사도·그룹 제약을 걸었지만 일부는 우연히 그럴듯한
  결합일 수 있다(예: 소통 방식 이야기에 "메일로 받는 게 편해요"). `orig_reason=X1` 행을
  팀에서 표본 검수하고, 애매한 행은 제거·교체할 것.
- **쉬운 negative 위주** — 시나리오 그룹이 다른 결합이라 화제 차이가 크다. 실전의 어려운 케이스
  (업무방 A의 메시지를 업무방 B에)는 이 데이터로 못 만든다. → 실사용 로그 또는 주제가 가까운
  멀티룸 코퍼스로 hard negative를 보강해야 한다.
- history 길이가 1~4턴 — 운영 설계(N=10~20)보다 짧다. 실서비스 문맥 분포와 다르다.
- 신규 잡담 history 20종은 재사용된다(평균 1.5회). 규모 확장 시 다양화할 것.
- v1의 "알려진 한계"(합성 데이터, 규모, 검수 필요)는 그대로 상속된다.
