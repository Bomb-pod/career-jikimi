# 문맥 적절성 데이터셋 v2.5 (확장분)

> v2의 커버리지 한계 4가지(긴 문맥, 메신저 문체, hard negative, 단체방)를 좁히는 확장.
> **학습은 `dialogue_context_dataset_v25_combined.csv`(v2 520 + 확장 224 = 744행)로 한다.**

## 1. 구성

가상의 채팅방 **16개**를 직접 작성했다. 방마다 history(10~16턴) 1개 + 그 방에서 적절한
응답 7개. 방은 8쌍으로 묶여 **서로의 응답을 교환**한다 — 방 A의 응답이 방 B에 가면
부적절("잘못 보낸 메시지"). v2와 같은 짝 구조라 누출이 원천 차단된다:

- 모든 response: 자기 방(적절) 1회 + 파트너 방(부적절) 1회 → response-only = 정확히 50%
- 모든 history: 적절 7회 + 부적절 7회 → history-only = 정확히 50%

| 교환 쌍 | 난이도 | 성격 |
|---|---|---|
| 앱 리뉴얼 TF ↔ 서버 이전 TF | **hard** | 같은 회사 프로젝트방끼리 — 인명·일정 추적 필요 |
| 마케팅 캠페인 ↔ 채용 | **hard** | 같은 회사 1:1 존댓말 |
| 대학 팀플 ↔ 동아리 축제 | **hard** | 같은 대학 반말 단체방 |
| 제주 여행 ↔ 등산 모임 | **hard** | 같은 야외활동 도메인 |
| 가족 ↔ 동창 | medium | 반말 모임 계획끼리 |
| 연애상담 친구 ↔ 형제 | medium | 반말 1:1 |
| 코테 스터디 ↔ 게임 내전 | medium | 반존대 vs 게임체 |
| 연인 ↔ 중고거래 | easy | 격식·화제 모두 상이 (고전적 착각 사례) |

부적절 112행 = hard 56 / medium 42 / easy 14. 단체방 62%, 평균 12.1턴.
문체: 잡담방은 카톡체(ㅋㅋ/ㅠㅠ/ㅇㅋ/끊어치기/이모지), 업무방은 업무체.

### 작성 규칙 (확장 시에도 지킬 것)

1. **모든 응답에 방 고유 앵커(인명·날짜·사물) 최소 1개** — "응 알겠어" 같은 일반 맞장구는
   어느 방에서도 적절해서 부적절 라벨이 성립하지 않으므로 금지.
2. history 마지막 화자는 상대방, 직접 질문으로 끝나지 않음(응답이 질문 무시가 되는 것 방지).
3. 교차 시 앵커가 받는 방 문맥과 우연히 겹치지 않는지 개별 확인
   (예: 채용방 "목요일 답 왔어요" → 마케팅방 목요일 일정과 혼동 → "지원자분" 앵커 추가).

### 추가 컬럼

`room_id`, `origin_room`(응답의 출신 방), `difficulty`(hard/medium/easy — 평가 슬라이스용),
`party`(group/1:1), `register`, `style`, `source`(v2/v25). 모델 입력은 여전히 history+response만.

## 2. 검증

| 검사 | 확장분 단독 | 통합본 | 기준 |
|---|---|---|---|
| response-only | 0.500 | 0.500 | ≤0.55 |
| history-only | 0.500 | 0.508 | ≤0.55 |
| history 셔플 | 0.519 | 0.500 | ≤0.60 |
| 관계 특징(어휘+격식) | **0.598** | 0.687 | 표면 특징보다 높을 것 |

확장분에서 관계 특징 baseline이 0.68 → **0.60**으로 떨어진 것은 의도된 결과다:
hard negative는 어휘 중첩·격식만으로는 못 풀고 의미·개체 추적이 필요하다.
파인튜닝 모델이 여기서 baseline과 얼마나 벌어지는지가 핵심 관전 포인트이며,
**difficulty별 성능을 반드시 나눠서 볼 것** (hard에서만 무너지면 개체 추적 실패라는 진단).

## 3. 학습 시 주의 (v2 규칙에 추가)

- 분할은 `pair_id` 단위 유지. **같은 방(room_id)의 행이 train/test에 걸치는 것도 피하는 편이
  엄격하다** — 방 단위 그룹 분할이 가장 보수적인 평가.
- `source`별(v2/v25), `difficulty`별 정확도·precision을 따로 보고할 것.

## 4. 한계

- 방 16개 × history 1개 — history 다양성이 제한적(각 history가 14행에 반복).
  실서비스도 같은 방 문맥이 반복되므로 구조적으로는 자연스럽지만, 방 수 확장이 다음 과제.
- 카톡체·오타·축약은 작성자(AI) 모사이며 실제 사용자 분포와 다를 수 있음.
- 여전히 합성 데이터 — 최종 검증은 웹앱 실사용 로그가 필요.
