# career-jikimi

> 채팅창을 착각해 잘못 보내는 메시지. 제가 당신의 회사생활을 지켜드리겠습니다.

| 항목 | 내용 |
|---|---|
| 문서 종류 | 프로젝트 명세 및 기술 문서 |
| 버전 | 2.0 |
| 최종 갱신 | 2026-08-03 |
| 대상 시스템 | 문맥 불일치 메시지 사전 경고 채팅 애플리케이션 |
| 상태 | 웹앱·판정 모델 구현 완료, 성능 평가 1차 완료 |

---

## 1. 개요

### 1.1 목적

본 프로젝트는 사용자가 채팅방을 착각하여 전송하려는, 해당 대화 문맥에
맞지 않는 메시지를 **전송 이전에 탐지하여 경고**하는 시스템을 구현한다.

### 1.2 구성

프로젝트는 세 갈래로 구성한다.

| 구분 | 내용 | 상태 |
|---|---|---|
| 1. 채팅 웹앱 | 경고 기능을 실제로 체험할 수 있는 채팅 애플리케이션 | 구현 완료 |
| 2. 데이터셋 구축 | 대화 스니펫 · 후보 메시지 · 라벨 | v3 1,000행 구축 완료 |
| 3. 판정 성능 평가 | 판정 모델의 탐지 성능 측정 | 1차 평가 완료 |

### 1.3 설계 원칙

**false positive를 최우선으로 억제한다.** 정상적인 메시지에 경고 팝업이
반복 노출되면 기능 자체가 사용 불가능해진다. 따라서 recall보다 **precision을
우선 지표**로 채택하며, 판정 임계값·데이터셋·평가 기준 전반이 이 원칙을 따른다.

## 2. 시스템 구성

### 2.1 기술 스택

| 계층 | 기술 |
|---|---|
| 프론트엔드 | React 18, TypeScript 5.7, Vite 6, Zustand (상태 관리) |
| 백엔드 | FastAPI, Python |
| 실시간 전송 | WebSocket |
| 데이터베이스 | MariaDB (InnoDB, `utf8mb4`) |
| ORM · 마이그레이션 | SQLAlchemy + `asyncmy`, Alembic |
| 판정 모델 | A.X-Encoder 파인튜닝 모델 (기본) / OpenAI API / Ollama 선택 가능 |
| 배포 | Docker, docker-compose |
| 시험 | pytest (백엔드), Vitest + Testing Library (프론트엔드) |

데이터베이스 문자셋은 `utf8mb4`로 **명시적으로 지정한다.** 기본값이 아닐 수
있으며, 지정하지 않으면 한글 및 이모지가 손상된다.

### 2.2 저장소 구조

```
backend/
  app/
    auth/         인증 (회원가입·로그인·JWT)
    friends/      친구 등록
    rooms/        채팅방 · WebSocket 엔드포인트
    messages/     메시지 저장 · 조회 · 이력
    judgment/     문맥 판정 (백엔드 선택, 익명화, 평가, 보고)
    core/         설정 · DB · 오류 · WebSocket 레지스트리
    models/       ORM 모델
  models/
    context_checker/    파인튜닝 인코더 모델 및 임계값
  migrations/     Alembic 마이그레이션
frontend/         React 클라이언트
dataset/          학습 · 평가 데이터셋
training/         모델 학습 및 평가 노트북
docs/             기술 문서
aidlc/            AI-DLC 산출물
```

### 2.3 주요 설계 결정

| 결정 | 근거 |
|---|---|
| 저장 후 브로드캐스트 | 순서가 반대이면 DB 쓰기 실패 시 화면에는 표시되나 새로고침 시 소실된다 |
| 정렬 기준을 `(room_id, seq)`로 지정 | `created_at`은 동시 도착 시 순서가 보장되지 않는다 |
| WebSocket 연결을 사용자당 1개로 유지 | `room_id` 멀티플렉싱으로 방마다 연결을 새로 열지 않는다 |
| 서버를 단일 프로세스로 고정 | 연결 레지스트리가 프로세스 메모리에 존재하므로, 다중 워커 구성 시 다른 워커에 연결된 사용자에게 메시지가 전달되지 않는다 |
| AI 검증 토글을 참여자 개인별로 적용 | 본 기능은 사용자 자신의 실수를 방지하는 기능이므로, 타인이 전송 지연 여부를 결정해서는 안 된다 |
| 판정 로그 테이블을 초기부터 도입 | 성능 측정이 목적인 시스템에서 메시지 테이블만으로는 실험 데이터가 축적되지 않는다 |

`seq` 채번은 단일 트랜잭션 내에서
`SELECT last_seq FROM rooms WHERE id=? FOR UPDATE` → `+1` → `INSERT`로 수행한다.
InnoDB 행 잠금이 적용되어 **방 단위로만 직렬화**되며 다른 방의 전송을 차단하지 않는다.

수평 확장이 필요한 경우 Redis pub/sub 도입을 검토한다.

## 3. 기능 명세

### 3.1 인증

- 회원가입 및 로그인을 제공하며 인증 수단으로 JWT를 사용한다. 만료는 기본 1,440분.
- 브라우저 WebSocket은 커스텀 헤더를 지원하지 않으므로, 연결 직후 첫 프레임으로
  인증 토큰을 전송한다.

### 3.2 친구

- 아이디 **정확 일치** 검색을 통한 **단방향 즉시 등록** 방식이며 승인 절차를 두지 않는다.
- 등록 시 별칭 입력을 필수로 하며, 등록 후 수정할 수 있다.

### 3.3 채팅방

- 친구를 다수 선택하여 방을 생성하며, 방은 복수로 생성할 수 있다.
- 방 헤더에 AI 검증 토글을 상시 노출한다. 신규 방의 기본값은 **켜짐**이다.
- 개인별 설정은 `room_members.ai_check_enabled` 컬럼에 저장한다.

### 3.4 메시지 전송

```
클라이언트 (임시 ID로 낙관적 렌더링)
   → 서버: 판정(활성화된 경우) → DB INSERT → 방 참여자에게 브로드캐스트
   → 클라이언트: ack의 실제 ID로 교체
```

### 3.5 대화 이어보기

- `GET /rooms/{id}/messages?before=<seq>&limit=50` — `seq` 커서 페이지네이션.
- 방 입장 시 **구독을 먼저 수행하고 이력을 이후에 조회한다.** 순서가 반대이면
  그 사이에 도착한 메시지가 유실된다. 중복분은 메시지 ID로 제거한다.

## 4. 문맥 판정 시스템

### 4.1 판정 백엔드

판정 엔진은 `.env`의 `JUDGMENT_BACKEND` 값으로 선택한다. 세 백엔드는 동일한
`ModelCall` 인터페이스를 반환하므로, `service.judge()`의 처리 절차와 판정 로그,
강행 전송, 보고 기능이 모두 동일하게 동작한다.

| 값 | 판정 엔진 | 비고 |
|---|---|---|
| `encoder` | A.X-Encoder 파인튜닝 모델 (로컬 추론) | **성능 평가를 완료한 기본 채택 구성.** 외부 전송이 발생하지 않는다 |
| `openai` | OpenAI API | |
| `ollama` | 로컬 LLM (Qwen 등) | OpenAI 호환 엔드포인트를 사용하므로 `openai`와 동일한 코드 경로를 공유한다 |

백엔드마다 점수 척도가 상이하므로 **임계값을 공유하지 않는다.** 실제 적용된
임계값은 `judgment_logs.threshold`에 기록되어 사후 재현이 가능하다.

### 4.2 판정 입력 규격

```
최근 N개 메시지 + 전송 예정 메시지  →  적절 / 부적절
```

- `N`의 기본값은 **10**이다 (`AI_CONTEXT_N`).
- **참여자 정보는 사용하지 않는다.** 대화 문맥만을 입력으로 한다.
- 화자 호칭은 등장 순서에 따라 `A`, `B`, `C` …로 **익명화**하여 모델에 전달한다.
  학습 데이터에도 동일한 규칙을 적용하여 학습·운영 간 입력 형식을 일치시킨다.
- 실제 사용한 문맥 범위를 `context_from_seq` / `context_to_seq`로 기록한다.

### 4.3 전송 흐름 (판정 활성 상태)

1. 전송 요청 시 전송 버튼을 비활성화하고 "확인 중..." 상태를 표시한다.
2. 판정 결과에 따라 분기한다.
   - **적절** — 그대로 전송한다.
   - **부적절** — "이 방에 맞지 않는 것 같습니다. 그래도 보낼까요?" 팝업을 표시한다.
     - 전송 선택 시 `flagged_sent` 상태로 전송한다.
     - 취소 선택 시 전송하지 않으며 입력창의 텍스트를 유지한다.

### 4.4 예외 처리

**콜드 스타트** — 방 내 메시지가 `N`개 미만인 경우 판정을 생략하고 전송한다.
문맥이 존재하지 않으면 판단이 불가능하다. 해당 건은 `skipped_no_context`로
기록하여 성능 집계에서 제외한다.

**판정 실패** — 타임아웃은 4초이며 재시도는 1회로 제한한다. 실패한 경우
사용자에게 고지 없이 전송하지 않는다. 사용자는 검증이 수행되었다고 인식하고
있기 때문이다.

첫 실패 시 1회에 한하여 계속 진행 여부를 확인하며, 사용자가 수락하면
degraded 상태로 전환한다.

| 항목 | 규격 |
|---|---|
| 적용 범위 | 사용자 전역. API 장애는 방 단위로 발생하지 않는다 |
| 유지 기간 | 세션 단위. 새로고침 시 초기화하고 정상 판정을 재시도한다 |
| 회복 감지 | degraded 상태에서도 5번째 메시지마다 1회 판정을 시도한다. 성공 시 정상 복귀 및 알림, 실패 시 팝업 없이 유지한다 |

별도의 헬스체크를 두지 않는 이유는, degraded 구간에서는 판정 API를 호출하지
않으므로 회복 여부를 확인할 수단이 없기 때문이다. 프로브 방식은 추가 인프라
없이 이를 해결한다.

판정을 거치지 않은 메시지에는 **"검증 안 됨" 배지**를 표시한다.

## 5. 데이터 모델

### 5.1 `messages.verification_status`

| 값 | 의미 |
|---|---|
| `ok` | 판정 통과 |
| `flagged_sent` | 부적절 판정 후 사용자가 전송을 강행 |
| `disabled` | 판정 토글이 비활성 상태인 방 |
| `skipped_no_context` | 문맥 부족 (콜드 스타트) |
| `failed` | 판정을 시도하였으나 오류 또는 타임아웃 발생 |
| `degraded` | 사용자 동의 하에 판정을 생략 |

`failed`와 `degraded`를 통합하지 않는다. 통합할 경우 API 장애 빈도를 집계할 때
degraded 구간이 혼입되어 과대 집계된다.

### 5.2 판정 로그 (`judgment_logs`)

| 컬럼 | 비고 |
|---|---|
| `message_id` | nullable — 사용자가 취소한 건은 메시지가 생성되지 않는다 |
| `room_id` | |
| `context_from_seq` / `context_to_seq` | 실제 모델에 입력한 문맥 범위 |
| `verdict` | 적절 / 부적절 |
| `confidence` | 판정 점수 |
| `threshold` | 판정에 적용한 임계값 |
| `latency_ms` | 판정 지연 |
| `prompt_tokens` / `completion_tokens` | 비용 추적 (LLM 백엔드) |
| `user_action` | `sent` / `cancelled` — **사실상의 정답 라벨** |

취소된 메시지는 `messages`에 저장되지 않고 판정 로그에만 남는다.

### 5.3 집계 기준

두 집계를 구분한다.

| 집계 | 대상 | 용도 |
|---|---|---|
| 메시지 기준 | `ok` + `flagged_sent` | 전송된 메시지의 판정 분포 |
| 판정 로그 기준 | `user_action`이 기록된 전체 건 | **precision 추정.** 취소 건이 포함되어야 성립한다 |

메시지 기준 집계만으로는 취소 건이 누락되어 precision을 산출할 수 없다.

## 6. 판정 모델

### 6.1 모델

| 항목 | 내용 |
|---|---|
| 기반 모델 | `skt/A.X-Encoder-base` |
| 학습 데이터 | `training_dataset_v3_1000` (1,000행, 적절 500 / 부적절 500) |
| 입력 | history + response (참여자 정보 미사용, 화자 익명화 적용) |
| 검증 방식 | `pair_id` 기준 StratifiedGroupKFold 5-fold 교차검증 |
| 배포 형태 | `backend/models/context_checker/` (약 300MB), CPU 추론 |

학습 데이터는 **고유 response 500건 전원이 적절·부적절 양쪽 라벨에 등장**하도록
구성하였다. 응답 표면만으로는 원리적으로 정답을 맞힐 수 없으므로, 성능이
확보된다면 그것은 문맥을 사용한 결과로 해석할 수 있다.

### 6.2 임계값

운영 임계값은 **0.7**이다. 적절·부적절 두 집단 사이에 0.687의 빈 구간이 존재하여
0.20~0.80 범위 어디에서도 평가셋 정확도가 1.000으로 동일하나, 적절 측 여유
(0.539)가 부적절 측(0.148)보다 크다는 점을 근거로 비대칭 선택하였다.
false positive 억제를 우선하는 설계 원칙에 부합한다.

임계값 결정 순서는 `ENCODER_THRESHOLD` → `threshold.json` → `AI_VERDICT_THRESHOLD`이다.

## 7. 성능 평가

측정일 2026-07-31 · CPU 추론 · 임계값 0.7. 상세는 `docs/판정_성능_보고.md` 참조.

### 7.1 평가 결과

| 지표 | 오발송 탐지 (`test_dataset_100`) | 지시 위반 (`test_dataset_100_hard`) |
|---|---|---|
| AUC | 1.000 | 0.728 |
| 정확도 | 1.000 | 0.510 |
| **precision** | **1.000** | **1.000** |
| recall | 1.000 | 0.020 |
| false positive | **0건** | **0건** |
| 절제 실험 AUC 하락폭 | −0.362 | −0.232 |
| p50 지연 | 512ms | 375ms |

두 평가셋 모두 학습 데이터와 **중복 0건**이다.

### 7.2 문맥 사용 여부 검증

응답은 고정하고 history만 다른 행의 것으로 교체하여 재판정하였다.

```
AUC    1.000 → 0.638   (−0.362)
정확도 1.000 → 0.550   (−0.450)
```

문맥을 훼손하면 판별력이 소실된다. 이는 성능이 응답 문체의 암기에서 비롯된
것이 아니라는 직접적 근거이다.

### 7.3 설계 범위 밖 입력

`test_dataset_100_hard`의 부적절 50건 중 46건(92%)은 **동일한 방 내에서
발생한 지시 위반·사실 불일치**로, 방을 착각한 오발송이 아니다. 이는 본
시스템의 설계 범위 밖이며, recall 0.020은 기능 실패가 아니라 다른 능력을
측정한 결과이다.

주목할 점은 **범위 밖 입력에서도 false positive가 0건**이라는 것이다. 팝업률
0.01로, 학습하지 않은 유형을 만나면 경고를 발생시키지 않고 통과시킨다.
precision을 우선하는 설계에서 이는 올바른 실패 양상이다.

### 7.4 지연

| | p50 | p95 | 4초 초과 |
|---|---|---|---|
| 오발송 셋 | 512ms | 534ms | 0건 |
| hard 셋 | 375ms | 377ms | 0건 |

타임아웃 예산 4초를 여유 있게 충족한다. 다만 위 수치는 배치 32 처리량 기준이며
단일 요청 지연은 별도 측정이 필요하다.

컨테이너 기동 후 첫 판정은 모델 로딩(약 300MB)을 포함하여 수 초가 소요되므로,
`main.py` 기동 시점에 `backend.warmup()`을 호출하여 이를 선행 처리한다.

### 7.5 해석 시 유의사항

**평가셋 규모가 100행이다.** 적절 50건에서 false positive가 0건이라는 결과의
95% 신뢰 상한은 약 0.060이며(rule of three), 이를 적용하면 실사용 기저율에
따라 precision이 크게 달라진다.

| 실사용 기저율 | 추정 precision |
|---|---|
| 10% | 0.649 |
| 5% | 0.467 |
| 1% | 0.144 |

**오발송 발생률이 1%인 환경에서는 팝업 7건 중 6건이 오탐일 수 있다.**
실사용 기저율은 `judgment_logs.user_action` 축적을 통해 확정한다.

또한 `test_dataset_100`은 response-only 기준선만으로 0.840이 산출되는 데이터로,
학습 데이터보다 난이도가 낮다. AUC 1.000을 일반적 성능으로 확대 해석해서는 안 된다.

## 9. 제약 및 한계

| 항목 | 내용 |
|---|---|
| 판정 범위 | **방 착각으로 인한 오발송**에 한정한다. 동일한 방 내의 지시 위반·사실 불일치는 탐지 대상이 아니다 |
| 문맥 길이 정합성 | 학습 데이터의 history는 중앙값 3개 메시지(최대 15개)이며 5~9개 구간의 표본이 존재하지 않는다. `AI_CONTEXT_N` 조정 시 학습 분포와의 정합성을 확인해야 한다 |
| 실사용 precision | 미확정. 기저율에 의존하며 판정 로그 축적으로 산출한다 |
| 단일 요청 지연 | 미측정. 배치 처리량만 측정하였다 |
| 확장성 | 서버 단일 프로세스 구성. 다중 워커 구성 시 WebSocket 브로드캐스트가 동작하지 않는다 |
| 이미지 크기 | 인코더 백엔드 사용 시 약 1.3GB 증가(CPU torch 약 750MB + 모델 300MB) |

### 프라이버시

`encoder` 백엔드에서는 대화 내용이 **외부로 전송되지 않으며 전량 로컬에서
처리된다.** `openai` 백엔드를 선택한 경우에 한하여 최근 `N`개 메시지가 외부
API로 전송되며, 이 경우 해당 사실을 사용자에게 고지한다.

## 10. 향후 과제

1. **실사용 기저율 확정** — `judgment_logs.user_action` 축적을 통해 실사용
   precision을 산출하고, 필요 시 임계값을 재조정한다.
2. **동일 방 내 사실 모순 대응** — 동일한 history에 날짜·인명·수량만 어긋난
   response 쌍을 설계하여 데이터셋을 확장한다. 오발송 탐지와는 별개의 능력이다.
3. **단일 요청 지연 측정** — 실사용 조건에서의 응답 시간을 확정한다.
4. **평가셋 확대** — 100행 규모로는 false positive율의 신뢰구간을 좁힐 수 없다.
5. **오프라인 재판정** — 판정이 비활성인 방의 메시지에 배치 재판정을 적용하여
   추가 평가 데이터를 확보한다.
